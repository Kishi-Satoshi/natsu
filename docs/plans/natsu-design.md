# NaTsu — Notion に寄せた議事録とチームのワークスペース

## Context

最初の依頼: 「UI含めて、Notionに限りなく近くに寄せて欲しいです。」
壁打ちで広がった依頼:
- 名前を NaTsu に変え、保存先まで含めて改める。ロゴは箱型にする。
- 要約をクラウドで行う（AWS のサーバーレス構成＋Bedrock の Claude）。
- プライベートとチームスペースを分け、ページごとに共有する。タスクも共有する。
- データベース、話者分離、AI による名前の修正を入れる。
- 個人の Claude と MCP で連携する。
- Teams で知らせる。ヘルプセンターを置く。

今の画面（調査結果）:
- **見た目:** ガラス風（ぼかし玉・`backdrop-filter`・グラデーション・ピル型・青い影）。Notion の平らな白地とは正反対。
- **画面の切り替え:** 上のタブ（議事録・音声入力・設定）は画面を切り替えるだけ。左の一覧は議事録タブの中にしかない。
- **ブロック:** 4種（見出し・箇条書き・ToDo・段落）。
  - Enter は空の行を足すだけ、Backspace は空の行を消すだけ。
  - `/` メニュー・Markdown 記法・型の変換がない。
  - 挿入や削除のたびに、ページ全体を描き直す。
- **一時停止:** 録音バーにすでにある（`overlay:pause`、`meeting.paused`／`pausedMs`）。

**全体を通して守ること**
- **出典の照合:** `src/cite.js` は変えない。照合の対象は箇条書きと ToDo だけ。`markdownToBlocks` が作る型も変えない（見出しの段数 `level` を足すだけ）。
- **録音バー:** `overlay.html` は触らない。例外は第0回の `<title>Listener Overlay</title>` の文字の置き換え1か所だけ。
- **Notion の資産:** デザイン資産・ロゴ・コードは使わない。フォントは OS 標準、アイコンは絵文字か自作の SVG。
- **Notion の考え方の扱い:** 考え方だけを参考にし、名前と実装は NaTsu のものにする。参考にしてよいのは、公開されている資料（ヘルプセンター・公式 API・公式ブログ）と、画面の外から見て分かる動きだけ。利用者が自分の PC で調べて作った試作（PoC）からは、Notion 以外の公開資料（Electron・SQLite・Node の公式資料）に同じ形が書いてある仕組みか、今の NaTsu のコードにすでにある形だけを採る。公開資料で説明できない形・名前・値（例: 間引きの秒数、会議の区画や状態の名前）は採らない。アプリの中を調べて分かった名前（モジュールの名前・設定の名前・内部の値）は、コードにも文書にも書かない。コードのコメントに「Notion は〜」と書かない。利用者の試作（PoC）のコードは、許しがあっても貼らず、落ちるテストから書き直す。
- **録音の守り:** 録音・下書き（`draft.json`）・音声の控え（`segbuf/` の WAV と `recovery.json`）は今までどおりファイルに書き、議事録の DB（第2a1回から）に頼らない。DB が止まっても録音は続く。
- **アプリの依存:** npm の依存を足さない。サーバー（`server/`）だけは Bedrock 用 SDK を使ってよい。
- **Claude Code の扱い（第1c回から。2026-10-18 の利用者の決定）:** NaTsu は、利用者が自分で入れてログインした Claude Code（`claude`）を、そのまま子のプロセスとして呼ぶだけにする。Claude Code の本体を同梱・改変しない。`~/.claude/.credentials.json` やトークンを読まない・写さない・しまわない。Claude のログインの画面を NaTsu の中に作らない（ログインは利用者が Claude Code 自身で行う）。子のプロセスの環境から `ANTHROPIC_` で始まる変数と `CLAUDE_CODE_OAUTH_TOKEN`・`CLAUDE_CODE_USE_BEDROCK`／`_VERTEX`／`_FOUNDRY` などを外し、呼ぶ前に `claude auth status` で「claude.ai のログイン」で動くことを確かめ、API キーの従量課金で動く設定なら呼ばない。`--bare` は使わない（OAuth のログインを読まない）。代わりに `--safe-mode` で、利用者の CLAUDE.md・フック・プラグイン・スキル・MCP・自動メモリを読み込ませない（利用者の設定は書き換えない）。オンラインのときに手元の LLM へ黙って切り替えない。
- **音声と文字の外への送り方（第1c回から）:** 外へ送るのは、利用者が設定で同意したときだけ。通信はすべて Electron の `net`（`net.request`）で行い、グローバルの `fetch` で外へ出ない（今の `loopbackOnlyFetch` の守りのまま）。クラウドの文字起こしの鍵は `safeStorage`（Windows では DPAPI）でしまい、`settings.json`・`engine.log`・画面・知らせに出さない。`engine.log` に文字起こしや要約の本文を書かない。
- **IME:** 確定の Enter は、どの新しい入力経路でも `imeEnter(ev)` で先に抜ける。
- **公開前の確認:** 個人名・社名・会社のドメイン・個人のパスをコードに残さない。会社のドメインはサーバーの環境変数にだけ置く。
- **テストデータ:** 実在の人名を使わない。出典リンクを LLM に作らせない。日付を推測で埋めない。
- **PowerShell:** BOM 付き UTF-8 と CRLF で保存する。`switch` と `[ValidateSet]` は使わない。
- **Listener の利用者:** 一切考えない。Listener の利用者向けには、データの移行も、自動更新の橋渡しも作らない（第0c回の「入れ直しの予告版」は NaTsu の利用者向け）。

## 目的（ソクラテス式の問答で分かったこと）

- **本当の目的:** 会社が50人に Notion を入れる予定を、NaTsu に置き換えること。理由は **Notion の料金**。今 Notion を使っているのは利用者本人だけで、導入を決めるのも本人。
- **最優先:** **50人が個人で使えること**。共有（チームスペース・同時編集・コメント）は後回しでよい。
- **1.0.0 の範囲:** 個人で使える版を **1.0.0** として50人に配る。共有などは 1.x で足していく。
- **1.0.0 の約束:** 配った後は、50人の議事録を壊さないことが最も重い約束になる。だから、保存の形の作り替え（T4b）は 1.0.0 の前の第2a1回で済ませる（どう作り替えるかは下の「保存の土台」。SQLite に切り替えるかは P2 で聞く）。ファイルのまま残る設定・下書き・復旧の控えの守り（壊れたときに消さない・読めなかったものを上書きしない）は、それより前の第1a回（JS）で入れる。
- **配る前に要らないもの:** PC が壊れて議事録が消えることは、配る時点では許せる（クラウド保存は配った後）。計算式とロールアップも、配った後でよい。
- **要約（50人全員が Claude の個人プランを契約している前提。Claude Code が含まれるプランかは「利用者に確かめること（第1c回）」の C3）:**
  - **2026-10-18 に変えた（利用者の決定。下の「利用者が決めたこと（オンラインの処理）」）:** 手元の LLM（llama.cpp）の要約は不安定なので、**手元の処理（手元の whisper と手元の llama）はインターネットにつながっていないときだけ**使う。オンラインのときは手元の LLM を使わない。
  - **自動の要約と［要約を生成］（第1c回から）:** オンラインのときは、利用者が自分の PC に入れてログインした **Claude Code を NaTsu がヘッドレスで呼ぶ**（`claude -p`、文字起こしは標準入力、`--output-format json`）。各自の Claude のサブスクリプションの利用枠（5時間ごと・週ごとの上限を Claude の利用と分け合う）で行い、**API の従量課金はかからない**ようにする（API キーで動く設定なら呼ばない。「全体を通して守ること」の Claude Code の扱い）。上限・ログイン切れのときは平易な言葉で理由と［もう一度］を出し、手元の LLM へは黙って切り替えない。オフラインのときだけ、今までどおり手元の llama で入れる。~~録音が終わったら手元の llama で自動で入れる~~（2026-10-18 に取り消し）。
  - **前の決め「NaTsu は Claude を一度も呼ばない」は取り消す**（2026-10-18）。NaTsu が呼ぶのは利用者自身の Claude Code だけで、NaTsu が Claude の API やログインを持つことはない。
  - **質の高い要約・書き戻し（第15回）:** 本人が Claude デスクトップで頼み、Claude が NaTsu の MCP で文字起こしを読んで要約を書き戻す形は残す（Claude Code の要約は MCP を使わない。MCP は Claude デスクトップから頼むときのため）。
  - **AI による名前の修正:** これも各自の Claude で MCP 越しに行う。
- **文字起こし（2026-10-18 に決めた。第1c回から）:** オンラインのときは**クラウドの文字起こし**（75秒の区切りの WAV を1つずつ送る。言語は ja、認識ヒントは辞書と直前の発言）。オフラインのときは今までどおり手元の whisper。どちらで処理したかを区間ごとに決め、ページに出す。送り先（Groq の無料枠・OpenAI・Azure の日本東リージョンなど）は「利用者に確かめること（第1c回）」の C1。録音の音声が PC の外へ出るので、前の約束「録音の音声は PC から出さない」は改め、利用者ごとの設定（同意）と、はっきりした知らせ（1on1・面談の注意を含む）を置く。
- **1.0.0 に AWS は要らない:** ログインも要らない。AWS・ログイン・管理画面は、共有を作る段階B へ移す。
- **決め手:** 50人が Notion でなくてよいと思う決め手は「見た目と書き心地が Notion と同じ」こと。そのため、画面と編集（第1b〜3回）は削らない。
- **Claude デスクトップ:** 50人の PC に入れられる。PC の中の MCP で足り、1.0.0 に AWS は要らない。
- **タスク:** 1.0.0 では自分の中だけで管理する。他の人への依頼は今までどおり Teams で行う。
- **NaTsu でいくことは決定済み:** 配った後の声は、段階B の順番を決めるのに使う。
- **1.0.0 の問い合わせ:** Teams の NaTsu 用チャンネルで受ける。アプリの「?」には、同梱した使い方の記事と、「状態を写して Teams に貼る」ボタンを置く。写すのは版の番号と動作の記録だけで、議事録の本文は含めない。サーバーは要らない（第3回で入れる）。ヘルプセンターと「その場で質問」は段階B。
- **Claude の書き込みの戻し（1.0.0）:** Claude が MCP で書き換える直前のページを、PC の中に控える（ページごとに直近10回分）。「…」→「Claude の変更を戻す」で戻せる。本物の変更履歴は段階B の第10回のまま（第15回で入れる）。
- **50人への案内:** 個人向けのプランでは、会話を学習に使うかの設定を本人が決める。1on1・面談を扱う前に、学習への利用を切るよう案内する（ヘルプの記事と、MCP の登録画面に書く）。

## 保存の土台（利用者の試作（PoC）を受けて。2026-10-17）

**何を変える案か（得と損）:** 前の計画では、保存の作り替え（T4b）は JSON のファイルのまま「ページの写し＋未送信の操作の列」にするはずだった。利用者の試作（PoC）を受けて、議事録の保存を SQLite の DB（`natsu.db` という1つのファイル）に切り替える案に変えた。利用者は 2026-10-17 に切り替えると決めた（下の「利用者に確かめたこと」の P2）。
- **得:** 2文字の語（「会議」「見積」）や句読点をまたぐ語でも、全部の文字起こしからすぐ見つかる（今は文字起こしのファイルを順に読み、長いものは途中で打ち切る）。2,000 ページでも一覧が速い。発言の直しと出典の付け直しが1回の書き込みで済み、途中で落ちても半端が残らない。毎日の確かめ済みの控えから戻せる。Claude（MCP）の書き込みも同じ守りを通る。後のクラウド保存（第7a回）で送る「操作の列」が初めからそろう。
- **損:** アプリの土台（Electron）を 31 から 44 に上げるため、全員がインストーラーで入れ直す（第0c回。P3）。段階A はおよそ1か月延びる（目安。第0c回で1〜2週、第2a1回が JSON のまま作り替えるより2〜3週）。1つのファイルが壊れると全部の議事録が読めなくなる（JSON なら1ページで済んだ）ので、控えと戻しで守る（RF11）。
- **設計で足した決まり（利用者の答えではない）:** 保存のファイルが1つ壊れただけで全部の議事録が読めなくなることは許さない（確かめ済みの控えから戻す。第2a1回）。1.0.0 の後に表の形を変えるときは足すだけにし、移す前に必ず控えを取る。

**試作（PoC）の扱い:** 利用者が自分で書いた最小の試作（`db-server.js`・`main.js`・`preload.js`・`state-store.js`・`package.json`・`README.md`）を受け取り、全部読んだ。利用者は Electron 44.9.0（Node 24.22.0・SQLite 3.53.4）で動くことを確かめている。試作に Notion のコードそのものは見当たらない。ただし、コメントと、表や操作の欄の名前には、アプリの中を調べて分かった名前や値が含まれている。だから NaTsu には、試作の名前も、数値も、データの形も持ち込まない。採るのは下の表の考え方だけで、1行ずつ Notion 以外の出典か NaTsu の理由を付けた（右の列）。試作は「どの公開資料を読めばよいか」の手がかりとしてだけ使い、NaTsu のコードは落ちるテストから書き直す。

**採るもの**

| # | 考え方 | NaTsu での形 | Notion 以外の出典か NaTsu の理由 |

| 1 | **書き手は DB 専用のプロセス1つ** | 議事録の DB に書くのは `utilityProcess` 1つ（`serviceName` は `NaTsu DB`）だけ。Claude（MCP。第15回）の書き込みも、このプロセスに頼む（下の「書き手は1つ」）。ファイルは `<userData>/data/natsu.db`（= `%APPDATA%\natsu\data\natsu.db`）。Chromium が消す `databases` という名前のフォルダには置かない | Electron の公式資料（`utilityProcess`）。NaTsu の理由: 録音とホットキーを受け持つ main を、DB の同期の処理で止めない |

| 4 | **表の形の版** | 版を DB の中に数え、1段ずつ上げる。アプリより新しい版の DB は、読み取り専用で開いてその旨を出す（書かない・落ちない） | SQLite の公式資料（`user_version`）。NaTsu の理由: 古い版に戻した人の DB を壊さない |
| 5 | **1つの命令 = 1つのトランザクション＋操作の記録** | 命令ごとに1トランザクションで書き、同じトランザクションで操作の列（`oplog`）に1行足す。操作には新しい値と前の値を入れる（試作の記録は値を持たず、当て直しも同期もできなかった）。同じ命令を送り直しても1回しか効かない（下の「送り直し」。試作では「書けたのに返事が届かない」が実際に起きた） | SQLite の公式資料（トランザクション）。NaTsu の理由: 前の計画の T4b の「操作の列」、第2b回の「元に戻す」、第7a回の同期で使う |
| 6 | **命令の一覧（ホワイトリスト）** | 画面から SQL は受け付けない。`app`・`main` の役は main が口に付け、MCP の口（第15回）には DB のプロセスが `mcp` の役を付ける。役ごとに使える命令を絞り、引数は型・ID の形・長さ・件数の上限まで照らす。エラーにパスや SQL を出さない。記録（`engine.log`）には件数と符号だけを書き、題名や本文は書かない（`engine.log` は Teams に貼られることがある） | Electron の公式資料（セキュリティの手引き: 画面から来るものを信じない）。NaTsu の理由: 段階B で他人の内容を表示する |
| 7 | **全文検索（FTS5 の trigram）** | 検索用に折りたたんだ文字の欄 `fold`（今の `cite.searchFold`。`cite.normalize` は変えない約束なので使わない）を JS で作って保存し、そこに索引を張る。**trigram は1〜2文字の語（「会議」「見積」「AI」）を見つけない**ので、1〜2文字は `fold` を `LIKE` で探す。入力は検索の文法として扱わない。抜き出し（スニペット）は元の文から JS で切る | SQLite の公式資料（FTS5・trigram）。NaTsu の理由: 今の `searchFold` と同じ当たり方を保つ（RF12） |
| 8 | **控え（スナップショット）と壊れたとき** | 処理を止めずに控えを取り、確かめる。壊れていたら**消さずに** `.broken-<時刻>` へ退け、確かめ済みの最新の控えから戻し、抜けたかもしれない期間を知らせる | SQLite の公式資料（オンラインバックアップ・`quick_check`）、Node の公式資料（`backup()`）。NaTsu の理由: 1ファイルが壊れても全部を失わない |
| 9 | **会議 = 1ページに3つの区画** | 要約・文字起こし・メモ（N4 の細いタブと同じ）。要約はページの本文のブロック、文字起こしは `segments` の行、メモは当面ページの欄 `memo`（メモをブロックで書けるようにする回で、メモ用のブロックに変える） | NaTsu の理由: 今の NaTsu がすでにこの3つを持っている（`pages/` の本文・`transcripts/`・`memo`） |

**送り直し（`tx`）:**
- 送り直しの鍵は、DB のプロセスが (役, `tx`) で作る。同じ鍵が来たら、前の行と命令の名前・`page_id` が同じかを確かめ、同じなら「済み」、違えばエラーを返す（「済み」とは言わない）。

**操作の列と、消した内容の残り方:**

**第2a1回の実装計画へ申し送ること（実装の細部）:**
- 開くときの設定: WAL・`synchronous=FULL`・`foreign_keys=ON`・`busy_timeout`。表は STRICT。`%APPDATA%` がネットワークの場所なら `journal_mode=DELETE`（P9）。
- 版は1段ずつ `BEGIN IMMEDIATE` の中で上げる。
- 命令の表は `Object.create(null)` を凍らせ、`Object.hasOwn` で引く（`__proto__`・`constructor` の名前を通さない）。
- 全文検索: 外部内容の trigram 表を、素の SQL の trigger で合わせる（`content_rowid` は `rid`）。入力はいつも引用の形に組み立て、`"`・`AND`・`NEAR` を文法として扱わない。1〜2文字は `LIKE ? ESCAPE '\'` とし、`%`・`_`・`\` を逃がす（逃がさないと `%` 1文字で全部の行が当たる）。作業環境の試しでは、30万発言で trigram が約 0.4 ミリ秒、1〜2文字の `LIKE` が 0.12〜0.17 秒。
- 控え: `backup()` で `data/backup/natsu-<時刻>.db` に取り、`quick_check` と全文検索の表の `integrity-check` を `worker_threads` で行う（同期で重い）。確かめた接続は必ず閉じる。
- 表の定義から JS で登録した関数を呼ばない（他の接続 ― MCP や SQLite の道具 ― が開けなくなる。素の接続で開けるテストで固定する）。
- 索引に条件を付けない（条件を書き忘れた問い合わせは索引を使わず、2,000 ページで 16 ミリ秒が 13.6 秒になった）。
- 読むときに組み立てるブロックの形は `{...attrs, id, type, text, rich, children}`（決まった名前を最後に置き、`attrs` が本当の欄を上書きしないようにする）。`attrs` に決まった名前（`id`・`type`・`text`・`rich`・`children` など）があれば、書き込みを断る（ST4）。

## 作り方（Superpowers の進め方。すべての回で必ず使う）

Superpowers（公開のプラグイン。確かめた版 bb92a77）の進め方で作る。作業環境にプラグインが入っていないこともあるが（今の作業環境には入っていない。P1）、そのときも下の決まりをそのまま守る（入っていれば、同じ名前のスキルを呼んで従う）。スキルとこの設計書が食い違うときは、この設計書を優先する（計画の置き場所は `docs/plans/` のまま）。

1. **brainstorming:** 回を始める前に、設計書で決まっていないことを平易な言葉で聞く。点検役のエージェントに設計書を「作る人」の目で読ませ、問いを「答えが書いてある／自分で決めて印を付ける／利用者にしか答えられない」に分け、最後のものだけを聞く。問いはまとめて1回で聞く（この作業は利用者が離れていることが多いため。Superpowers の「1つずつ聞く」からの意図した違い）。答えは設計書に書き、承認されるまでコードを書かない。確かめのための下書きのコードは捨てる前提で作り（利用者の試作（PoC）とは別のもの）、残すときは改めてこの手順を通す。
2. **writing-plans:** 各回の直前に `docs/plans/<日付>-<回>.md` を書く。頭に目的・方針・使うもの・設計書・全体の決まり（そのまま写す）・Review Focus（テストの無い、起きそうな失敗5つ。それぞれ持ち主のタスクでテストを持たせる）・ファイルの地図。タスクごとに触るファイル・受け渡す名前と形・5手（落ちるテスト → 落ちるのを見る → 最小の実装 → 通るのを見る → commit）。最後に自己点検の5項目（設計書を覆っているか・手順の抜け・名前と形の食い違い・Review Focus・大きさの釣り合い）。利用者に見せて承認をもらってから作る。
3. **using-git-worktrees:** この作業環境ではブランチを作業環境が決めるので、worktree は作らず、決められたブランチ（`claude/…`）で作る（Superpowers からの意図した違い）。main では作らない。始める前に `npm test` が全部通ることを確かめる。
4. **test-driven-development:** 本番のコードは、落ちるテストを先に書き、正しい理由で落ちるのを見てから書く。テストより先に書いたコードと、捨てる前提の下書きのコードは使わず、テストから書き直す（例外は利用者の許しがあるときだけ）。利用者の試作（PoC）のコードは、許しがあっても貼らない（「全体を通して守ること」）。
5. **subagent-driven-development:** タスクごとに新しいエージェントが作り、別のエージェントが「計画どおりか」と「質」の2つを点検する。作り手は並べて走らせない。直しは1タスク5回まで（1〜3回目は同じ作り手、4〜5回目はより強いモデルの新しい作り手。直すたびに点検し直す）。進み具合と判断（Ruling: 何を・なぜ・外れたときの損）は台帳に書く。回の最後に、回全体をもっとも強いモデルで点検する。使うモデルはいつも名前で指定する。
6. **requesting-code-review／receiving-code-review:** 点検はタスクごとと回の最後に、元と先の commit（BASE・HEAD）とタスクの文を渡して頼む。指摘はコードで確かめてから直す。重大と重要は次へ進む前に直し、軽いものは台帳に残す。間違った指摘には理由を添えて返し、利用者が決めたことと食い違う指摘は利用者に聞く。直しは1つずつ、テスト付きで行う。
7. **verification-before-completion:** 「できた」「通った」と言う前に、その場で確かめる。`npm test` が `# fail 0`、`node tools/risk.js --staged` が BLOCK 0、CI が Linux と Windows の両方で緑、変異確認（直しを1つ戻すと決めたテストが赤、戻せば緑）。エージェントの「済み」は git の差分で確かめる。
8. **systematic-debugging:** テストや CI が赤のときは、原因を突き止める前に直さない（記録を読む・再現する・最近の変更を見る・仮説を1つずつ最小の変更で試す）。直しが3回続けて外れたら止めて、作りを利用者と相談する。
9. **finishing-a-development-branch:** 回の終わりに全部のテストを通してから、出し方（手元で merge／push して PR／そのまま残す）を利用者に選んでもらう。リリースは `release/natsu-v0.x.0` のブランチを push し、`release.yml` が両方の OS の CI が緑のときだけ出す（プロキシがタグの push を止めるため）。force-push と作業の破棄は、利用者が言ったときだけ行う。

**作っている途中で止まって利用者に聞くのは4つだけ:** 取り返しのつかない操作、安全に関わる操作、外への影響（main への merge・リリース）、計画が壊れていてどの道も当て推量になるとき。それ以外は判断して台帳に書き、回の終わりに「決めたこと」として一覧で見せる。回の始めの問い（brainstorming）と、実装計画の承認は、これとは別に必ず行う。

**台帳の置き場所:** 台帳・作り手への指示・点検用の差分は git に入れない（`.superpowers/` は第0c-1回の EL0 で `.gitignore` に足す。それまでは作業環境のスクラッチパッドに置く）。残る記録は commit。プラグインが無いときは、指示（タスクの文）と点検用の差分（`git log --oneline BASE..HEAD`・`git diff --stat`・`git diff -U10`）を手でファイルに書いて渡す。

**設計書を行番号で指さない:** 各回の実装計画は、設計書を行番号ではなく、見出し（例「第0c回」「保存の土台」）と項目の記号（例 EL4・ST10）で指す。設計書は直すたびに行がずれる（2026-10-17 の直しでも約100行増えた）。第0a回・第0b回の計画と `notion-behavior.md` にある行番号の指し先はもう古いので、それぞれを次に直すときに見出しと記号に直す。`notion-behavior.md` の「章と回の対応」の「2a」は、編集の動き（1〜7章）は 2a2、18章（公開 API のブロックの形）は 2a1 と読む（次にその文書を直すときに書き換える）。

**テスト（JS）:**
- Linux の CI（`node --test`）: 文字コードごとのバイトの見本（UTF-8・BOM 付き・UTF-16LE／BE の BOM 付きは読める。CP932 は化けずに退けられる）。途中で切れた・空・末尾が NUL・形の違うファイルは、元と1バイトも違わない `.broken-` が残り、既定と記録の1行と知らせが出る。パスがフォルダ・ずっと `EACCES` なら投げず、ファイルは書き換わらない。`EBUSY` が3回の後に読めれば値が残る。名前の変更が2回失敗して3回目に通る。ずっと失敗すれば一時ファイルが消え、元が残り、書き手が止まったままにならない。`fsync` が名前の変更より先（`fs` を差し替えて順を見る）。同じ中身なら書かない。残った一時ファイルの片付け。まとめ書き: 間隔の中の2回の変更が新しいほうの1回の書き込みになる・タイマーの中の失敗で例外が出ず、次の変更で書ける・`unref` したタイマーでも終わりの書き出しで残る。退けない読み方では、壊れたファイルが元の場所に元のまま残る。作り直せないファイル（設定・履歴）と今の形（ミリ秒の数）の `.broken-` は、いくつあっても消えない。

**保存の形（第2a1回で決め、あとで作り直さない）**:
- **ブロックは木:** 画面と API では `children` を持つ木にする。DB では子が `parent_id` と並びの鍵 `ord` を持ち、読むときに `children` を組み立てる（上の「保存の土台」）。第8回の同時編集も、第16回の段組み・同期ブロックも、この形を前提にする。
- **文字は2つの欄で持つ:** 今までどおりの素の文字 `text`（文字列）と、飾り付きの区切りの列 `rich`（例 `[{t:"今日は",m:[]},{t:"大事",m:["b"]}]`）。保存のたびに（DB の命令の中で）`rich` から `text` を作り直し、両方が食い違わないことをテストで固定する。`rich` に知らない飾りの名前や、`http(s)`・`mailto`・`natsu` 以外のリンクがあれば書き込みを断る（SEC2 をデータの入口でも守る）。
- **素の文字の使い道:** `cite.js` は `b.text` を文字列として読んでいるので、そのまま `text` を読ませる。だから `cite.js` は変えない。DB の層はブロックを `{...attrs, id, type, text, rich, children}` の形に組み立てて返す（決まった名前を最後に置き、`attrs` が本当の欄を上書きしないようにする。ST4 で `attrs` の決まった名前を断る）ので、`cite.js` は今どおり `b.text`・`b.cites`・`b.citeState`・`b.assignee` を読める（照合の前に木を平らにする）。検索・要約・コピーも `text` を使う。
- **見出しの段数:** 今の `markdownToBlocks` は `#`〜`####` を区別せず `heading` にしている。`#`→1、`##`→2、`###` 以下→3 とし、読み取りのテストを足す。
- **既存のページ:** 「子のない木」として読む。
- **出典チップ:** 箇条書きと ToDo 以外の型に変えると、その行の出典チップは消える（許容する）。要約の有無の判定（`heading` があるか）は変わらない。

### Electron の版の守り方（第0c回から）
- **固定する:** 版は `package.json` にきっちり固定する（`^` は使わない）。上げるたびに全員が一度入れ直すので、決めた時期のほかには上げない。
