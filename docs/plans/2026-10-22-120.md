## 目的

1. **（D53・D66）議事録の文字起こしの行に「自分」「相手」が付く。** 相手の声を取り込む会議では、マイクの音と相手の声を別々に録って別々に文字起こしし、「自分」（マイク）と「相手」（PC から流れた声）を音の入口で決める（音の大きさで推し量らない）。2つの流れの行は始まりの時刻の順に1本の並び（タイムライン）にまとめ、声が重なった所は両方の行を残す。ページ・録音中の画面・Claude から読んだ文字起こし（0.10.0 の MCP）・要約への入力と Markdown の写し（D58 の Q21）に出る。
2. **費用を音声の長さで増やさない。** 流れごとに区切りと声のあるなし（VAD）を持ち、無音を中継へ送らない（決めたこと 123〜125）。要求の数は増える（約 1.5〜2 倍）ので、中継の CPU と Cloudflare の無料の上限への効き目を 0.9.4 の中継の作り直しと合わせて見積もり、持ち主に問う（決めたこと 131・問い S14）。
3. **録音を壊さない。** 区間の送りの順・一時停止・終了・破棄・打ち切り・下書きからの戻し・無音で自動で止める（0.9.1）・遅い PC の音声を残す（0.9.4）が、2つの流れでも今と同じに動く。

## 調べた結果（D66 で足した。`746ea67` と 0.9.4 の計画）

A1. **今は混ぜて1本で録っている:** 相手の声を取り込む会議では、マイク（`getUserMedia` の `echoCancellation`・`noiseSuppression`・`autoGainControl` は true: `overlay.html:564`〜`:569`）と相手の声（`openSystemStream`: `:560`。Windows の既定の再生の機器のループバック: `src/loopback.js`）を、1ch の `mixBus`（`gain 0.9`）→ `mixDest` で混ぜ、`mixDest.stream` を MediaRecorder で録る（`:583`〜`:640`）。開始のビープはループバックに乗るので、鳴らす瞬間だけ `sysGain` を閉じる（`muteSystemForBeep`）。相手の声のトラックが途中で終わると、マイクだけで録り続け、`reportSource(false, true)` で知らせる（`:615`〜`:625`）。混ぜる形を前提にしたテストは `test/runtime.overlay.test.js:26`（`systemAudio: true` で録って止めると音声が渡る）だけで、混ぜ方そのもの（`mixBus`）を見るテストは無い。
A2. **main の区間は1本の並び:** `onMeetingSegment(buffer, durationMs, isFinal)`（`src/main.js:4531`）は1つの `m.offsetMs` に長さを積んで `atMs` にし、ID は届いた順の `s${++m.seq}`、文字起こしは1本の鎖 `segChain`。認識ヒントは直前の済んだ区間の末尾（`promptTail(m.segments)`: `:4573`）、作り話の繰り返しの見張りは直前の 1〜2 区間の文（`:4624`〜）。無音の区間（一番大きい 0.5 秒の窓が `SILENT_DBFS` = −55 dBFS より小さい）は経路を決める前に送らない（0.9.1 Q-2: `:2028`〜`:2031`）。無音で自動で止める見張り（`noteHeard` → `lib.quietStep`: `:3602`）は、区間の終わり `atMs + durationMs` が増えていく並びを前提にしている。
A3. **PC の whisper は VAD が既定で入っている:** `useVad: true`（`src/settings.js:104`）で、whisper-server を `--vad --vad-model` で起こす（`src/main.js:840`〜`:841`）。エンジンの中で無音を飛ばすので、PC の計算は「声のある時間」に比べて増える。ただし whisper は 30 秒の窓で処理し、15 秒の区間も 30 秒分を計算する（0.9.4 の計画の調べた結果の 9）。0.9.4 の記録では、持ち主の PC は会議中に1本の流れでも追いつかない（処理 ÷ max(音声, 30 秒) が 1.15〜2.1）。
A4. **中継の1要求の重さ（0.9.4 の後）:** 文字起こしの1要求ごとに、止めたメールの照らし（D1 の SELECT 1 回: `relay/access.mjs:215`）、取り置き（`reserveUsage`: D1 の batch に upsert 2・読み 2・古い行の DELETE 1: `relay/limits.mjs:36`〜`:40`）、失敗したときの戻し（UPDATE 2: `:51`）。秒は要求ごとにバイト数から切り上げ（`Math.ceil`: `relay/stt.mjs:55`）。0.9.4 の S-6 で本文を貯めずに流すので、1要求の CPU は WAV の大きさにほとんどよらない（残るのは鍵の照らしと D1 の待ちの外の JS の仕事）。0.9.4 の S-5 は中継の 5xx が 2 回続くと 60 秒〜10 分の間、中継へ送らない（`relay-hold`。会議の全部の区間に効く）。
A5. **Cloudflare の無料の上限（2026-10-22 に公式の頁で読んだ）:** Workers Free は 1 日 100,000 要求・1 要求の CPU 10 ms（https://developers.cloudflare.com/workers/platform/limits/ 。越えると Error 1027）。D1 の Free は 1 日に読み 500 万行・書き 100,000 行（INSERT・UPDATE・DELETE の行。索引の分も足される。00:00 UTC で戻る。越えると問い合わせが誤りになる: https://developers.cloudflare.com/d1/platform/pricing/ ）。1 呼び出しの問い合わせは Free で 50 まで。
A6. **クラウドの文字起こしは時刻を返さない:** 中継のモデルは `gpt-4o-transcribe`（`relay/config.mjs:20`）で、答えは `json`（文だけ）。文の時刻（`verbose_json`・`timestamp_granularities`）は OpenAI の資料では whisper-1 のもの（作る前に OpenAI の音声の資料で確かめる）。だからクラウドの側の行の時刻は「区間の始まり」で、行を細かくするには区間を声の切れ目で切るしかない。
A7. **発言の並びと ID:** DB の `segments.n`（`src/db/schema.js:54` の索引）は `meeting.segments` の並びで、ID は届いた順。2つの流れを別々に文字起こしすると、届く順と時刻の順が食い違う（マイクの 0:10〜0:18 の区間が、相手の 0:12〜0:16 の区間より後に届く）。0.10.0 の箇所の窓と印（0.10.0 の計画の決めたこと 72・75）は並びの順を前提にしていたので、0.10.0 の決めたこと 113 で「時刻の順に読む・印の番号の大小を見ない」に直した（D66 への備え。0.10.0 の中では順は同じなので答えは変わらない）。
A8. **回り込み（ヘッドホンなし）:** 相手の声はスピーカーから出てマイクにも入る。Chromium の `echoCancellation` が消すのは、そのプロセス（NaTsu）が鳴らした音を手がかりにしたものと見込まれ、別のアプリ（Teams・Zoom のアプリ）の音は消えないことがある（見込み。実機 32 で確かめる）。混ぜて1本で録る今は、回り込んだ声も同じ1行に入るだけだったが、別々に録ると、同じ言葉が「相手」（ループバック）と「自分」（マイク）の2行に出る。
A9. **0.9.1 の止まりの見張り・0.9.4 の背圧と音声を残す道:** どれも1本の区間の並びの数（`pendingSegs`・`m.emptySegs`・`noteEmptySegment`）で決める。2つの流れでは、待ちの数がおよそ 2 倍に見える。

120. **（D66）2つの流れで録る:** 相手の声を取り込む議事録では、録音バーが MediaRecorder を2つ持つ。マイクの流れ（今の `micStream`。エコー消し・雑音消し・自動の音量はそのまま）と、相手の声の流れ（`sysStream` → `sysGain`（ビープの間は閉じる今の道）→ 1ch の `sysDest`）。混ぜる `mixBus` から録るのをやめる（点と印の analyser は今のまま）。相手の声を取り込まない会議（設定で切った・始めに取り込めなかった）と音声入力は、今の1つの録音のまま（`src` を付けない）。
121. **（D66）「自分」「相手」は音の入口で決める:** マイクの流れの区間は `src: 'mic'`、相手の声の流れの区間は `src: 'loopback'`。音の大きさで推し量らない（D56 の 8 割・替わり目の決まりは無い）。札は `SOURCE_LABELS` で引く。目安の注（`title`・記事・`instructions`）は「同じ部屋の人の声はマイクから入るので自分になる・ヘッドホンなしでは相手の声がマイクにも入ることがある（決めたこと 129 で除く）」の2つだけ。
122. **相手の声の取り込みが途中で切れたとき:** 相手の声の流れは、その時の区間を締めて送り（その流れの最後）、マイクの流れは続ける。切れた後に始まったマイクの区間には `src` を付けない（相手の声がスピーカーからマイクへ入っていても「自分」と言わないため。相手の声を取り込まない会議と同じ）。一時停止から再開して取り込めれば、また2つの流れに戻る（再開は今どおり流れを開き直す: `overlay.html:572` の注）。録音バーは区間を始めるときの取り込みの有無で、その区間の `src` を決めて送る。移り変わりはきっかけ（開始・一時停止・再開・取り込みが切れた・終了）と一緒に main の `m.srcLog` に積む（持ち主の試作の状態の履歴の形）。問い S11。
123. **（D66）流れごとの区切りと VAD（クラウドの側）:** main は2つの流れの議事録の間ずっと（録音中のページが見えていなくても）100ms ごとに `overlay:level-ask` を送り、答えの流れごとの大きさ（`mic`・`sys`。0.9.3 と同じ `rmsOf`）を `VOICE_LEVEL`（録音バーの `SILENT_LEVEL` と同じ 0.02）で「声あり・なし」にし、流れごとの純粋な `vadStep` を回す。切る合図（`overlay:cut { src, seg }`）は次の3つ:
    - **切れ目（pause）:** 声のあった区間で、声の無い時間が `PAUSE_CUT_MS`（700ms）続き、区間が `MIN_SEG_MS`（2 秒）以上。
    - **長い切れ目:** 声の無い時間が `LONG_PAUSE_MS`（1.5 秒）続いたら、区間が 2 秒より短くても切る（「はい」だけの区間も1行になる。次の発言とつなげない）。
    - **無音（idle）:** 区間の中に声が無いまま `IDLE_CUT_MS`（3 秒）たった（相手が黙っている間の区間を短く切って捨てる: 決めたこと 125）。
    上限は今の区間の時計（15 秒。0.9.4 のまま）で、録音バーが切る。PC の側（オフラインモード・PC の文字起こしに落ちた会議）は切れ目で切らない（決めたこと 128）。一時停止の間は数えない。数え方は区間ごとに `{ voicedMs, firstVoiceMs, silentRunMs }` だけ（話者は数えない）。
124. **始まりの時刻（atMs）は流れごとの時計から:** 録音バーは議事録の「録っている時間」（一時停止を除いた `performance.now()` の積み）を持ち、区間ごとに始めた時の値 `t0` を送る。main は2つの流れの会議では `atMs = t0 + 頭を切った分`（決めたこと 125）にする（1本の会議は今どおり長さの積み）。`t0` は照らす（数・0 以上・その流れの前の区間の終わり −1 秒以上・会議の録った時間＋5 秒以下。違えばその流れの長さの積みに倒す）。2つの録音の長さを別々に積むと、1 時間で数秒ずれうるため。
125. **無音を送らない:** (a) 無音（idle）で切った区間と、声のフレームが1つも無く一番大きい 0.5 秒の窓が `SPEECH_DBFS`（話し声の大きさ。今の値）より小さい区間は、中継へも PC へも送らず、ページに出さない（数は `m.emptySegs` と engine.log の「声の無い区間（相手の声）: 12」）。(b) 送る区間は、最初の声のフレームの `PRE_ROLL_MS`（300ms）前より前を WAV から切る（`wavFrom(buffer, ms)`。純粋）。切った分を `atMs` に足し、`durationMs` は残った長さ。(c) 今の 0.9.1 の無音の判定（`SILENT_DBFS`）は、その後にもう一度かかる（今のまま）。小さな声を落とさないため、(a) は「フレームに声が無い」と「WAV も話し声より小さい」の両方のときだけ。
126. **鎖と認識ヒントは流れごと:** 文字起こしの鎖を流れごとに持つ（クラウドへは2つが同時に出る。マイクの行が相手の行の後ろで待たない）。PC のエンジンは1つずつしか処理しないので、PC へ送る所だけは1つの門（`localGate`）を通して順に送り、門で待った時間は 0.9.4 の待ち時間（PC の時間切れ）に数えない。認識ヒント（`promptTail`）と作り話の繰り返しの見張り（直前と同じ文）は、同じ流れの区間だけで見る（相手の行と同じ文のマイクの行は、繰り返しとしてでなく回り込みとして決めたこと 129 で見る）。
127. **（D66）タイムライン:** 純粋な `timelineOf(segments)` が、発言を「行」（`{ id, ms, text, src, failed, kept, part }`）の並びにする: 時刻 `ms` の順（PC の側の `parts` は文ごとの行に分けてから並べる）。同じ時刻なら発言の並び（`n`）の順。声が重なった所は両方の行を残す（混ぜない・消さない）。ページ・録音中の画面（画面の写しの `timelineView`。`repo` が同じ表を両方に当てる）・写し（Markdown）・要約への入力・MCP（`segmentLines` と箇所の窓）の全部がこれを通る。DB の並び（`n`）は今どおり届いた順（書き込みの道を変えない）。
128. **PC の側は長い区間のまま、文の時刻で行に分ける:** PC の文字起こしの区間は流れごとに今の長さ（75〜90 秒）で、切れ目では切らない（whisper は 30 秒の窓で計算するので、短く切ると会議中に追いつかない）。無音はエンジンの VAD（`--vad`）が飛ばす。PC への要求を `response_format: 'verbose_json'` にし、答えの文の頭（`segments` の `start`）と区間の文の中の文字の位置から `parts: [{ ms, at }]`（最初は 0・0。2〜200 個）を作る（純粋な `partsOf(sentences, { text, durationMs })`）。文の時刻が無い（古いエンジン）・最後の `end` と区間の長さが 2 秒より大きくずれる・文をつないだものが区間の文にならない（`cleanWhisperText` で変わった）ときは `parts` を作らない（区間を1行に倒す）。読む側は `checkParts(parts, text, durationMs)` で照らし、違えば無いものとして読む。文を直したら（`segment.update`）`parts` を消す。2つの流れの長い区間を、文ごとの行でタイムラインに混ぜるため（行が 90 秒ごとに片方ずつになるのを避ける）。
129. **（問い S9 の勧め）回り込みを除く:** マイクの行の文（畳んだ形）が、時刻の重なる（前後 3 秒）相手の行の文に、文字の3つ組で 60% 以上（`BLEED_SHARE`）含まれていれば、そのマイクの行を「回り込み」として除く（純粋な `bleedOf(micText, loopTexts)`。どちらが先に文字起こしを終えても、後に終えた方の時に見る。利用者が文を直した行は除かない）。除いた数は engine.log の「相手の声の回り込みとして除いた行: 3」（文は書かない）。ヘルプと実機の案内で「ヘッドホンを勧める」。自分が相手と同時に話してマイクの行に両方の言葉が入った行は、文が違うので残る（その行の相手の言葉は「自分」に入る: 記事に書く）。
130. **最後と締め:** 録音バーは流れごとに区間の番号（`seg`）と「その流れの最後」を持ち、議事録の最後（`isFinal`）は「2つの流れのどちらも最後を送った時の、後の方の区間」に付ける（1本の会議は今のまま）。main は今どおり `isFinal` で締める。打ち切り（`skipPending`）・破棄・一時停止・終了は2つの流れに同じに効く。下書き・DB の写し・戻しは `src`・`parts` を今の道のまま運ぶ。
131. **費用と中継の重さ（見積もり。実機 33 で測って直す）:** 前提: 1 時間の Web 会議で、自分が 20 分・相手が 20 分話し、残りは黙っている・切り替わり。
    - **音声の秒（費用と中継の上限）:** 今は 60 分を全部送る。D66 の後は、声のある 40 分＋区間ごとの頭の 0.3 秒と終わりの 0.7 秒（約 400 区間で約 7 分）＋要求ごとの秒の切り上げ（約 3 分）で約 50 分。**今より約 2 割少ない**（無音を送らないため）。重なり・回り込み（ヘッドホンなし）ではその分増え、最大で今の約 2 倍。
    - **要求の数:** 今は 15 秒ごとに約 240 回。D66 の後は約 400 回（一言ずつの区間が増える）、長く話す会議では最大で約 480 回（2つの流れが 15 秒ずつ）。**約 1.7〜2 倍。**
    - **中継の CPU（Workers Free の 1 要求 10 ms）:** 0.9.4 の S-6 の後は1要求の CPU が WAV の大きさによらないので、区間が短くなっても1要求の CPU は今と同じ。2つの流れは同時に出るが、Workers の CPU の上限は1要求ごとなので、同時でも上限に近づかない（越え続けると止まる「続けて越える」は1要求の重さの話）。要求が 2 倍になると、1 日の CPU の合計（Paid での請求の元）が 2 倍になる。
    - **Cloudflare の1日の上限（調べた結果の A5）:** Workers の 100,000 要求は約 250 会議時間（1 日・全員の合計）、D1 の書き 100,000 行は、1 要求に約 2 行（取り置きの upsert 2。索引の分が足されればもっと）で約 125 会議時間。**今（約 240 回）は約 200 会議時間なので、上限に先に当たるのは D1 の書きで、今の約 6 割の会議時間で止まる。** 越えるとその日（00:00 UTC まで）は全員の文字起こしが中継で失敗し、PC に落ちる（0.9.4 の 5xx の間）。
    - **OpenAI の側:** 費用は音声の長さなので増えない（上の秒）。1 分あたりの要求の数（組織の段の RPM）は約 2 倍の速さで使う（作る前に管理画面で段の数を確かめる）。

132. **PC の計算（オフラインモード・PC に落ちた会議）:** エンジンの VAD が無音を飛ばすので、2つの流れの計算は「両方の声のある時間」に比べて決まり、混ぜた1本（どちらかが話している時間）と比べて、ヘッドホンありで約 1.1〜1.4 倍（重なりと、区間ごとの 30 秒の窓の端数）、ヘッドホンなしで最大約 2 倍（回り込みでマイクの流れにも相手の声が入る）の見込み。遅い PC では 0.9.4 の「音声を残して会議の後で文字起こし」が増える。問い S10。
133. **0.9.4 の背圧と見張り:** PC の側の背圧（待ちが 3 を越えたら長く）は、2つの流れの会議では待ちの数を流れの数で割って見る（1つの流れあたり 3）。0.9.1 の止まりの見張り（`noteEmptySegment`）は流れごと。0.9.1 の無音で自動で止める見張り（`quietStep`）は、**どちらの流れにも話し声が無い時間だけ**を数える（純粋な `quietUnion` で、2つの流れの済んだ区間の終わりの小さい方までを「決まった時間」として `quietStep` に渡す。相手が話している間は、自分が黙っていても止めない）。

## 受け渡す名前と形

**`src/mainlib.js`（SP-1。純粋。足すだけ）**
- `SOURCE_LABELS = Object.freeze({ mic: '自分', loopback: '相手' })`・`SPEAKER_LABELS = Object.freeze({})`（第13回で足す）・`VOICE_LEVEL = 0.02`（録音バーの `SILENT_LEVEL` と同じ。`repo` が字面で照らす）・`FRAME_MAX_MS = 250`・`PAUSE_CUT_MS = 700`・`LONG_PAUSE_MS = 1500`・`MIN_SEG_MS = 2000`・`IDLE_CUT_MS = 3000`・`PRE_ROLL_MS = 300`・`BLEED_SHARE = 0.6`・`BLEED_NEAR_MS = 3000`・`PARTS_MAX = 200`。

- `segAtOf({ t0, prevEndMs, offsetMs, activeMs })` → `atMs`（決めたこと 124 の照らしと倒し）。
- `timelineOf(segments)` → 行の配列（決めたこと 127）。`partsOf(sentences, { text, durationMs })` → `parts` か `null`・`checkParts(parts, text, durationMs)` → 写しか `null`（決めたこと 128）。

- `quietUnion(st, { src, kind, endMs })` → `{ st, feed }`（`feed` は `quietStep` に渡す `{ kind, endMs }` の配列。決めたこと 133）。
- `srcLabel(seg)` → `SPEAKER_LABELS[seg.speaker]` か `SOURCE_LABELS[seg.src]` か `''`（どちらも `Object.hasOwn` で引く。`'__proto__'` は `''`）。

**`src/renderer/overlay.html`（SP-2。`<script>` の中だけ）**
