## 目的

1. **PC 全体が重くならない。** 文字起こしのエンジンが、会議のアプリ（Teams・Zoom など）や画面の操作と CPU を取り合わない。
2. **会議中の遅れを小さくする。** 会議の後のやり直しが、会議中の区間の前に割り込まない。一度の悪い会議で「この PC は遅い」と 14 日決めつけない。
3. **止まって抜けない。** 落ちたエンジンが残ってポートを塞ぐ・同じ形で落ち続ける、を断つ。
4. **会議の後の文字起こしが必ず終わる。** 時間切れになる区間が1つあっても、ほかの区間と要約は進む。何度も時間切れになる区間は音声を残して止める（今の「3 回で保留」と同じ形）。
5. **更新すれば直る。** 前の版が残した設定（スレッドの数）・覚え（`local-pace.json`）・待ち行列（`recovery.json`）を、0.18.1 の初めの起動で直す。利用者は［設定］→［更新］で 0.18.1 にするだけでよい。

## 決めたこと（理由つき。持ち主の答えで直す。どれも AQ の (a) の形で書いた）

1. **スレッドの既定を半分に（AQ181-1 (a)）。** 既定 = `max(2, min(8, floor(論理 CPU / 2)))`（`settings.js` の `defaultSettings` と `main.js` の `CPU_DEFAULT_THREADS` を1つの関数 `lib.defaultThreads(n)` に）。12 論理 CPU → 6、8 → 4、4 → 2、2 → 2、32 → 8。理由: 会議のアプリと画面のための CPU を残す。whisper は 8 を越えると速さがほとんど伸びない。失うもの: 何もしていない PC での速さが少し落ちる（「遅い」と判じられる会議が増えうる。2 の優先度と 4 の覚えの直しで和らげる）。
2. **起こしたエンジンの優先度を「通常より低い」に（AQ181-1 (a)）。** `spawn` の後に `os.setPriority(p.pid, os.constants.priority.PRIORITY_BELOW_NORMAL)`（Node の公式の部品。Windows では BELOW_NORMAL_PRIORITY_CLASS）。失敗しても起こすのは止めず、`engine.log` に1行。理由: 画面と会議のアプリが先に CPU を取れる。失うもの: ほかの重い仕事（ビルドなど）と同時のときは文字起こしが遅れる。
3. **前の版の既定のスレッド数を、新しい既定へ移す（AQ181-1 (a)）。** 起動のとき（と `retrySettingsRead`）、`localThreads` が前の既定のどれか（`max(4, n − 2)`・`max(4, floor(n / 2))`）と同じなら新しい既定にする。今の `migrateOldThreads` と同じく、メモリの中だけ（書き戻し・知らせ無し）。理由: `settings.json` は既定の数をそのまま書いているので、利用者が選んだ数と見分けられない。失うもの: 前の既定と同じ数を自分で選んだ利用者も、新しい既定になる（［設定］で戻せる）。
4. **「遅い」の覚えに印を足し、印が違う覚えは無いものとする（AQ181-3 (a)）。** 覚えに `stamp`（エンジンの組の印（取り込んだ組の置き場の名前、手のパスなら `manual`）・スレッドの数・優先度の版 `2`）を足す。読むとき、`stamp` が無い・違う覚えは無いのと同じ（0.18.1 の初めの起動で、前の版の「遅い」は効かなくなる）。**覚えに「遅い」と書くのは、その会議で速さの数が 3 つ以上あり、理由が `two`・`big` のときだけ**（時間切れ1回・待ちだけで「遅い」になった会議は、その会議の中だけ遅いにし、覚えない）。理由: 一度の悪い会議・前の版の重さで 14 日決めつけない。失うもの: 本当に遅い PC では、次の会議の初めの何区間かを PC に送ってから「遅い」になる（今の 0.9.4 の形の初めの会議と同じ）。
5. **会議の後のやり直しで、時間切れを回数に数え、その区間を待ち行列の後ろへ回し、その回はそこで止める（AQ181-4 (a)）。** `late` の区間は `tries` を 1 上げ、3 回で `held`（今の「3 回で保留」と同じ。音声は残し、［もう一度文字起こし］で試せる）。保留でなければ待ち行列の後ろへ回し、その回のやり直しは止める（1 回の起こしで時間切れは1つまで＝PC を長く塞がない）。次の回はほかの区間から進む。`down`（エンジンが起きない）は今のまま（数えず、その区間から先を残して止める）。理由: 1 つの区間が全部を止めない・要約まで進む。失うもの: 時間切れの区間が後に回り、議事録の順に埋まらないことがある（区間の場所は変わらない。埋まる順だけ）。
6. **会議の後の待ち時間は、速さが分からないとき rtf を 3 とみる（AQ181-4 (a)）。** 会議の後の PC の頼み（`transcribeRecoveredItems` から）だけ、`localTimeoutMs` に `after: true` を渡し、rtf が空なら 3（90 秒の区間で 600 秒。上限の 30 分は今のまま）。会議中の区間は今のまま。理由: 会議の後は急がない。失うもの: 本当に止まったエンジンに気づくのが遅れる（会議の後だけ）。
7. **録音を始めたら、会議の後のやり直しの頼みを切り、エンジンを起こし直す。** 頼みに `AbortController` の `signal` を渡し、録音を始めたときに切る。切った区間は `busy`（数えず、待ち行列に残す。今の録音中の扱いと同じ）。切った頼みは whisper-server の中で走り続けるので、今の時間切れと同じ `restartWhisperAfterLate` の形でエンジンを止め、次の区間で起こし直す。理由: 会議の区間を待たせない（R5）。失うもの: 切った区間の計算は無駄になる（後でやり直す）。
8. **GPU で落ちる・止まるのが続いたら、その起動の間は GPU を使わずに起こす（AQ181-2 (a)）。** 取り込んだ GPU 版の組で、準備ができた後に落ちた（`down`）・時間切れ（`late`）が、同じ起動の中で合わせて 2 回になったら、次からその起動の間は同じ組に `-ng` を足して起こす。`engine.log` に1行（「文字起こしの計算: GPU で 2 回止まったので、この起動の間は CPU で計算します」）。覚えない（次の起動はまた GPU から）。理由: 落ちる GPU で同じことを繰り返さない。0.15.1 の「CPU版は使わない方針」の答えと食い違う（K1）ので、持ち主に問う。失うもの: GPU がたまたま1〜2回落ちただけの PC で、その起動の間は遅くなる。
9. **温度を上げての計算のやり直しを止める（AQ181-5 (a)）。** 頼みに `temperature_inc=0.0` を足す。1.9.5 の whisper-server がこの欄を読むかは、Task PF-5 の初めに `engine-smoke`（CI の Windows で本物のエンジンを動かす）で確かめる。読まないなら、この直しは外して持ち主に知らせる。理由: 雑音の区間が毎回時間切れになるのを防ぐ。失うもの: 聞き取りにくい区間の字が少し悪くなることがある（繰り返しの文は今も NaTsu が落とす）。
10. **前の NaTsu が残したエンジンを止めてから起こす。** 起こしたエンジンのプロセスの番号と exe の名前を `<userData>/data/engine-proc.json` に書き（`src/jsonfile.js`）、止めたら消す。起こすときポートが塞がっていたら、その記録の番号のプロセスが今も同じ名前（`tasklist` で照らす）なら止め、ポートが空くのを 5 秒まで待ってから起こす。名前が違えば今のまま（止めずに「ポートが使われている」）。理由: R8。ほかのアプリのプロセスは止めない。失うもの: 無い（記録の無い前の版の残りは、今の形のまま。0.18.1 の後の残りから効く）。
11. **ヘルプを直す。** `trouble/slow-pc.md` の「3 回まで試して」を、時間切れの区間も含む形に直し、スレッドの数の既定と、文字起こしが PC を重くするときの手（［設定］のスレッド数を下げる）を足す。字は Task PF-6 で作り、Task G で持ち主に見せる。
