2. 後でソースのリポジトリを非公開にしても、0.19.0 からのアプリの更新・インストーラーの取り込み・エンジンの取り込みが壊れない形にする（D102 の目的「計画書・開発の履歴・会社の事情を見せたくない」）。非公開にすること自体は、この版ではしない（AQ190-1）。
3. Electron を 45 の最新の安定版へ入れ替える（D104・AQ190-4。44 の支えは 2027-03-02 まで、45 は 2027-04-27 まで）。インストーラーで一度入れ直してもらう。
4. 前の版を使っている人が、0.19.0 の入れ直しまで迷わず進める（AQ190-2）。

## 決めたこと（理由と失うものつき）

1. **配る側のリポジトリは、持ち主が GitHub の画面で作る公開の `natsu-releases`（README だけ）。**（AQ190-3）手順は「持ち主の手でする所」の手順 1。中にソースは置かず、リリースに配る物を付けるだけにする。配る側では Actions を切る（そこでは何も走らせない）。理由: リポジトリと鍵は外から見える・権限に関わる操作なので、持ち主の手で作るのが確か。失うもの: 持ち主の手が要る（手順 1〜5 で 30 分ほどの見込み）。
2. **0.19.0 から、アプリの確かめ先・［ダウンロード］・`get-installer.ps1` を配る側に向ける。** `src/updater.js` の `REPO` を `<持ち主のアカウント>/natsu-releases` にする（定数は1つのまま）。［ダウンロード］の URL・`readFeed` の既定・エンジンのテストの結び付きは、今どおり `REPO` から作る。`get-installer.ps1` の `$repo` も同じにする（`test/identity.test.js` が照らす）。理由: 定数1つを替えれば、アプリの中の確かめ先がみなそろい、画面から URL を受け取らない形（`test/repo.test.js` の「外部URL」）も保てる。接続先のホストは同じなので、会社の許可の頼み直しは要らない（R9）。失うもの: 0.19.0 を入れた PC は今のリポジトリを見なくなる（今のリポジトリだけに出した版は届かない）。`get-installer.ps1 -Version <0.18.x 以前>` は配る側に無い版なので取れない（前の版は今のリポジトリのページから取る。「この回でやらないこと」）。
3. **0.19.0 は、今のリポジトリと配る側の両方に、下書きの通しの実行で作り、実機で確かめた同じバイトの物を出す（本番の実行で作り直した zip と exe は捨てる: 決めたこと 14・16。第4版で字をそろえた: 2回目の点検 2-d）。**（AQ190-2）0.18.x のアプリは今のリポジトリの latest に 0.19.0 を見て、入れ直しの知らせと［ダウンロード］を出し（0.19.0 の `natsu-update.json` の `electron` は `>=45.x.y` なので、0.18.x の Electron 44 は満たさない）、［ダウンロード］で今のリポジトリの 0.19.0 のページが開く。入れた 0.19.0 は配る側を見る。今のリポジトリへも出す版は、`release.yml` の決まった一覧 `SOURCE_TOO`（AQ190-7 の答えで `0.19.0` だけ。入れ直しが要る版をどうするかは AQ190-13: 決めたこと 18）で決め、一覧に無い版は配る側だけに出す。2か所の資産は、配る側に添付した物を今のリポジトリへ写す（決めたこと 16）。理由: 入れ直しは1回だけで、前の版のコードを変えずに済む。失うもの: 0.19.0 のリリースの流れが2か所へ出す形になり、流れとテストが増える。
4. **鍵は、配る側だけに効く細かい権限の鍵（Contents: write）を、ソースのリポジトリの環境 `dist`（Deployment branches は `release/*` だけ）の秘密 `DIST_TOKEN` に置く。**（AQ190-3）鍵を読む仕事は、`release.yml` の `publish` と `whisper-vulkan.yml` の `publish` の2つだけにする。どちらも ubuntu の小さな仕事で、リポジトリの取り出し・依存の取り込み（`npm install`）・テストを走らせず、作った物は前の仕事から artifact で受け、action は commit の SHA で固定する（別のモデルの点検 B2・CR3・CR5・CR13）。鍵はその中でも `gh` を呼ぶ段の `env` にだけ渡す（仕事の `env` に置かない）。最初に鍵で配る側を読み、401 なら下書きを1つも作らずに止める（「鍵の期限が切れたか、取り消されています。持ち主の手順 4 で作り直してください」）。この確かめは読めるかしか分からない（Metadata の読みは自動で付く）ので、書けるかの本当の確かめは、今のリポジトリのどの書き込みよりも前に配る側の下書きを作ること（M-a・CR9）。GitHub の答えに鍵の期限の見出し（`github-authentication-token-expiration`）があれば、期限の 30 日前から、リリースの要約に「配る側の鍵の期限が近い（YYYY-MM-DD）」と出す。期限は AQ190-10 の答えで 1 年。鍵を使う仕事に持ち主の承認の一押しを足すかは AQ190-12。理由: 毎日 `claude/*` や `lane/*` の枝を push するので、リポジトリの秘密の欄だと、どの枝のワークフローからも読める。環境なら `release/*`（main と同じく持ち主のはっきりした言葉の後だけ push する枝）の仕事だけが読める。さらに、同じ仕事の段どうしは隔たっていないので、鍵を持つ仕事で他人のコード（依存の install の台本・札で動く action）を走らせなければ、そのコードが鍵を読む道が無い。失うもの: 期限ごとに持ち主が作り直す。リリースのたびに環境の「Deployments」の記録がソースのリポジトリに1つ増える（鍵を使う仕事が1つなので実行ごとに1つ: M-d。害は無い）。仕事の受け渡し（artifact）が増える。
5. **`release.yml` の形（作り方の細かいことなので、作り手が選んだ。持ち主に問わない。第3版で別のモデルの点検 B1・B2・I3・I5・M-e を受けて直した）。**

**AQ190-16 配る側のリポジトリで、公開したリリースを変えられなくする設定（Immutable releases）をオンにするか:**

GitHub の文書（https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/immutable-releases ・ https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/preventing-changes-to-your-releases 。2026-11-28 に読んだ）によると、オンにすると、それより後に公開したリリースの添付のファイルは変えることも消すこともできなくなり、札もそのリリースがある間は消せなくなります（題・本文・先行版や latest の印は直せます）。リリースそのものは消せ、消した後は札も消せますが、同じ札の名前は二度と使えません。文書は、下書きで作って添付を全部付けてから公開する形を勧めています（第4版で直しました。第3版の「消すこともできなくなる」は言い過ぎで、第3版の別の所の「下書きの扱いは書いていない」も違っていました: 別のモデルの2回目の点検 2-4）。
- **(a) オンにする（おすすめ）。** 手順 1 に1つ足します（手順 1 の 10）。下書きの通しで、下書きを消して同じ札の名前で作り直せることを確かめます。理由: 鍵が漏れても、もう配っているインストーラー・更新の zip・エンジンを、同じ名前のままこっそり差し替えることはできなくなります（新しい版を出すことまでは防げません）。流れはもともと公開した後の資産に触らない形なので、流れは変わりません。失うもの: 公開した後に間違いに気づいても、同じ札では出し直せず、版を上げて出します（リリースを消しても、同じ札の名前は使い直せません）。リリース（例えばエンジンの先行版 `whisper-vulkan-d1be6fd` や `natsu-v0.19.0`）を間違えて、または漏れた鍵で消されると、その URL は二度と戻りません。エンジンなら、0.19.x を入れた全部の PC がエンジンを取り込めなくなり、新しい URL を持つアプリの版を出すまで直りません（オンにしなければ、同じバイトを同じ札で上げ直せ、中身が正しいかはアプリの SHA-256 のピンが守ります）。手順 5 のエンジンは、公開の前に下書きで SHA-256 を見る手順が増えます。

- **CR1（AQ190-4 の決まり。作る前から決めておく）:** Electron の版は、EL-2 を作る日の 45.x の最新のパッチにきっちり固定し（`npm view electron versions` で見る。2026-11-28 は 45.5.0）、選んだ版と日をここに書く。Task G でもう一度見て、新しいパッチが出ていれば上げて CI をやり直し、ここに書き足す。`engines.electron` はいつも `>=` その版。

- **CR2（B1）公開できるのは `release/<札>` の枝だけ:** 公開の段（配る側の公開・ソースの札・今のリポジトリの公開・一時ブランチの片付け）の `if` に `github.ref_name == format('release/{0}', needs.release.outputs.tag)` を入れ（`publish` は `needs: [release, installer]` なので読める。`help-redeploy` は `release` を直に挙げないので、CR16 の `publish` の出力 `finished` で見る。第3版はここに `help-redeploy` も入れていたが、その形では条件がいつも偽になる: 2回目の点検 2-1）、段の中でも `[ "$GITHUB_REF_NAME" = "release/$TAG" ]` を照らして違えば赤で止める。`publish` の入力は残す（`release/natsu-v*` の上でも下書きで止められる）。理由: 下書きの通しの枝の上では、入力をどうしても公開しない形にする（push で起きる `release/natsu-v*` では、札は枝の名前から決まるので、いつも通る）。失うもの: `release/<札>` でない枝からは公開できない（今も push で起きるのはその枝だけなので、困らない）。
- **CR3（B2 (1)）仕事の分け方:** `ci` → `release`（鍵なし・`contents: read`）→ `installer`（鍵なし・`contents: read`）→ `publish`（環境 `dist`・`contents: write`・`needs: [release, installer]`）→ `help-redeploy`（`needs: publish`）。`release` は zip・`natsu-update.json`・本文・ps1 2つを artifact `release-files` で、札・一時ブランチ・配る側の名前を仕事の出力（`tag`・`cleanup`・`dist_repo`）で渡し（`installer` も配る側の名前を要るので、artifact でなく出力にした。第4版で決めたこと 5 とそろえた: 2回目の点検 2-e）、`installer` は setup.exe を artifact `installer` で渡す（作ったときだけ。作ったかは出力 `built`: CR17）。`publish` は zip と情報を `release-files` からだけ取る（`npm` の入る仕事が作った物は exe 1つに限る）。今のリポジトリへの `gh`（下書き・公開・札・一時ブランチの片付け）も `publish` の中で `github.token` で行う（取り出しが無いので、一時ブランチは `gh api -X DELETE` で消す）。artifact は 14 日で消える設定にする（`whisper-vulkan.yml` と同じ）。理由: 同じ仕事の段どうしは隔たっていないので、鍵を持つ仕事で他人のコードを走らせない。失うもの: 仕事が1つ増え、artifact の受け渡しと `release.yml` とテストの直しが大きくなる。
- **CR4（B2・I3）exe を作るかの決め方:** `installer` は鍵を持たないので、配る側の下書きを見られない。`github.token` で、公開済みの配る側のリリース（誰でも見える）に exe があるかを見て、あれば作らない（公開の途中で止まった後のやり直し・AQ190-15 の2回目）。下書きしか無いときは作り、`publish` が、配る側の下書きにもう exe があれば作った exe を捨てて下書きの物を使う。理由: 配る exe はいつも最初に添付した1つになり、exe を作る仕事に鍵を渡さずに済む。失うもの: 本番の1回目など、下書きに exe がある実行で、exe を作る 10〜15 分が無駄になる。作らなかったときは artifact `installer` が無いので、`publish` は出力 `built` が `true` のときだけ落とす（CR17）。
- **CR5（B2 (2)）action の固定:** `release.yml` の action は全部 commit の SHA で固定し、右の注にその版を書く（`whisper-vulkan.yml` と同じ形。`actions/download-artifact` と `actions/upload-artifact` は `whisper-vulkan.yml:214`・`:233` と同じ SHA から始め、作る日に 4.x の最新を見る。`actions/checkout`・`actions/setup-node` も作る日の 4.x の SHA）。指摘は鍵を持つ仕事だけだったが、`release` と `installer` の action も配る物（zip・exe）を作るので、まとめて固定する。`ci.yml` ほかは鍵を持たず配る物を作らないので、この版では変えない（「この回でやらないこと」）。理由: 札は動かせるが、SHA は動かせない。失うもの: action の新しい版を取り込むのが手になる。
- **CR6（I1）ソースの札を作る時:** 指摘は「配る側の公開の後に作る」だったが、照らしが全部通った後・配る側の公開の「直前」に作る。札の注の1行目は「NaTsu <版>（配る側: <配る側の名前>）」、続けて配る側の資産の「名前 バイト SHA-256」を1行ずつ。札は `gh api repos/$GITHUB_REPOSITORY/git/tags`（注釈の札）と `…/git/refs`（`refs/tags/natsu-v<版>`）で作る。理由: 直前に作れば、配る側が公開済みなら必ずソースに札がある形になり、やり直しのときに「公開済みの配る側がこの commit の物か」を札で確かめられる（決めたこと 16 の (1)）。札を作っても `release.yml` は起きない（タグの起こし方は外し、`github.token` の操作はワークフローを起こさない）。失うもの: 札を作った後に配る側の公開で止まると、まだ出ていない版の札がソースに残る（同じ commit のやり直しはそのまま進む。別の commit で出し直すなら、持ち主の言葉の後に `gh api -X DELETE repos/$GITHUB_REPOSITORY/git/refs/tags/natsu-v<版>` か持ち主の画面で消す。この作業環境のプロキシは `refs/tags` の push を通さない見込みなので（`README.md:586`）、`git push origin --delete` は使わない。第4版で直した: 2回目の点検 2-b・CR20・M11）。
