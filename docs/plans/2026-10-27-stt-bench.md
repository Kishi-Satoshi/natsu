## 目的・方針

- **目的:** 持ち主の PC（Core i5-1335U〔10 コア・12 スレッド。P コア 2・E コア 8〕・16GB・Iris Xe・Windows 11 25H2・Zscaler・管理者の権限なし・Intel のグラフィックのドライバは会社の IT が入れる。配る 50 台も同じ機種）で、**今のモデルのまま計算を Iris Xe の GPU に移すと**、2つのつらさがどれだけ軽くなり、文が変わらないかを数で見せる。GPU が届かなければ、同じ音声で CPU の候補を測る。決めるのは持ち主。
- **方針:**
  - **段1（GPU）を先に、段2（CPU の候補）は段1 が届かないときだけ。** 段1 は A0 と D（＋flash attention を切った Dn を1本だけ）。同じ音声・同じ測り方なので、段2 に進んでも A0 と音声は測り直さない。
  - 測るのは持ち主の PC だけ（作業環境は Linux で、i5-1335U の E コアと Iris Xe を真似できない）。持ち主はスクリプトを1つ動かし、数だけの表を貼って返す。
  - 音声と文字はその PC から出さない。表には数だけを書く（会議の文・ファイルの名前・利用者のパスを入れない）。GPU の記録の行（パスが入る）も表に入れず、「GPU を使えたか」だけを読み取る。
  - 落とすものは全部、版か commit で固定した URL と、大きさ・SHA-256 で照らす（`src/engine-manifest.js` と同じ決まり）。**D の whisper.cpp は上流に Windows の Vulkan 版が無いので、NaTsu の CI が固定のタグから作り、SHA-256 を記録して、NaTsu の配布のリポジトリに先行版（prerelease）として置く**（下の「段1」。GQ2）。
  - GPU が使えないとき（Vulkan を読めない・初期化に失敗・途中で落ちた）は、**その回を「GPU の数ではない」と表に書く**。whisper.cpp は GPU が使えないと黙って CPU で続けるので、何もしないと CPU の数を GPU の数として読んでしまう。
  - NaTsu の設定・取り込んだエンジン・議事録には触らない。NaTsu が取り込んだモデルは、同じ中身（SHA-256）なら読むだけで使う。
  - 第0b回 Task 0（`tools/bench-summarizer.ps1`）の形を引き継ぐ: 続きから取れる取得・2回まで取り直す照らし・画面の案内どおりに Enter・NaTsu を測り中だけ終了・結果は数だけ。

### 道 1 の詳しいこと

**作り方（llama.cpp のリリースに合わせる）:** llama.cpp の `.github/workflows/release.yml`（`master`・`0c8c59ef`）の `windows:` のジョブは、`runs-on: windows-2025`・`VULKAN_VERSION: 1.4.357.0` で、LunarG の Vulkan SDK を `curl.exe` で落として `--accept-licenses --default-answer --confirm-command install` で黙って入れ、`VULKAN_SDK` を環境に足してから `cmake -DGGML_VULKAN=ON` で作る（`:1101`〜`:1185`）。whisper.cpp 自身の Windows のリリースのジョブ（`v1.9.5` の `release.yml:139`〜）は `-DBUILD_SHARED_LIBS=ON -DGGML_NATIVE=OFF -DGGML_BACKEND_DL=ON -DGGML_CPU_ALL_VARIANTS=ON` で作る。**この2つを合わせる**: whisper.cpp の旗に `-DGGML_VULKAN=ON` を足すだけ（README の「Vulkan GPU support」も `cmake -B build -DGGML_VULKAN=1` だけ）。Vulkan SDK 1.4.357.0 の Windows の入れ物は 287,971,024 バイト・SHA-256 `81f474711e9042f4cd22b31b2f7a8870db2e428b21586fb43dd80150be97310d`（2026-07-27。作り手が落として計算。最新は 1.4.363.0 だが、llama.cpp と同じ版にそろえる）。

**動かす側（持ち主の PC）:**
- ggml の Vulkan は Vulkan **1.2 以上**を求める（`ggml-vulkan.cpp:5194`）。Intel のドライバ 32.0.101.7085（2026-03-18。release notes の PDF）は「Vulkan 1.3: 11th Generation Intel Core processors and higher」で、13 世代の Raptor Lake-U と Windows 11 25H2 を載せている。会社の PC のドライバの版は分からない（同じ notes に「Corporate customers should always use OEM drivers」とあり、PC の作り手の版のことがある）→ 道具が表にドライバの版を書く。
- `ggml-vulkan.cpp` には Intel のための分かれ道が多い。たとえば **「Intel の Windows のドライバ 32.0.101.8509〜8860 は fwht の計算で落ちるので使わない」**（`:3564`〜`:3566`）・古い Intel の GPU で非同期の実行を切る（`:4183`。llama.cpp #17302）・Intel では subgroup の collectives を使わない（`:3787`）。**ドライバの版で動きが変わることが、コードに書いてある**（IT の更新で変わりうる。GQ6）。

**CPU へ戻る仕組み（whisper.cpp v1.9.5 のコード）:**
- `whisper-server`・`whisper-cli` は起動のときに `ggml_backend_load_all()` を呼び（`examples/server/server.cpp:642`・`examples/cli/cli.cpp:1059`）、exe のフォルダの `ggml-*.dll` を読む（`ggml-backend-reg.cpp:578`〜`:604`）。DLL は `SetErrorMode(SEM_FAILCRITICALERRORS)` のもとで `LoadLibraryW` で読む（`ggml-backend-dl.cpp:7`〜`:12`）ので、**`vulkan-1.dll` が無ければ、窓を出さずに Vulkan を飛ばす。**
- GPU の初期化に失敗しても、CPU の土台を足して続ける（`whisper.cpp:1340`〜`:1368`）。記録には「using Vulkan0 backend」の後に「failed to initialize Vulkan0 backend」が出る。
- **途中で GPU が落ちた（`DeviceLost`）ときは戻らない:** 例外のまま終わる（`ggml-vulkan.cpp:358` など）。NaTsu では whisper-server が落ちたのと同じになるので、「決まった後」で CPU で起こし直す仕組みが要る。
- `-ng`（`--no-gpu`）で GPU を使わずに動かせる（`cli.cpp:206`・`server.cpp:180`）。環境変数 `GGML_BACKEND_PATH` で、exe のフォルダの外の DLL を1つ足して読める（`ggml-backend-reg.cpp:600`〜`:604`。「決まった後」の案 b）。
- 記録の行の形（`load_backend: loaded CPU backend from …\ggml-cpu-alderlake.dll`）は、持ち主が 2026-10-17 の第0b回 Task 0 で送った `bench-E4B-cpu.md` にも出ている（`%LOCALAPPDATA%\natsu-bench` の DLL を、この会社の PC が読めた）。

**Intel の iGPU での報告（一次の出典。どれも Iris Xe の Windows の数ではない）:**

## 段1（GPU の試し）: 作る → 置く → 測る

### 1-1. CI で作る（このときはまだファイルを足さない。GQ3 の答えの後）

**ワークフローは、計画が承認されるまで `.github/workflows/` に置かない。** 理由: (1) 承認の前に作るものを足さない（CLAUDE.md）。(2) GitHub の「手で起こす」ワークフロー（`workflow_dispatch`）は、**既定のブランチ（main）にファイルがないと起こせない**（GitHub の文書「Manually running a workflow」: "To trigger the workflow_dispatch event, your workflow must be in the default branch."）。`lane/stt-bench` に置いても動かせず、main へは持ち主のはっきりした言葉なしに push しない。→ どこに置くかは GQ3。

- **全部を自分たちで作る**（CPU の DLL・exe も）。上流の b5454 の CPU 版に `ggml-vulkan.dll` だけを足す形は、作った時の道具（MSVC の版）が違うと DLL の間の取り決めがずれるおそれがある。測りでは全部を同じ作りにする（NaTsu に入れるときの形は「決まった後」で問う）。
- 作った zip は毎回 SHA-256 が変わりうる（zip の中の時刻）。だから **置いた資産の SHA-256 を、道具のピン（`bench-stt.ps1` の `whisperVkZip`）と計画に写す**。写すまで道具は D を測らない（`Size = 0` のあいだは飛ばし、段1 は止まる）。

### 1-2. 置く（GQ2）

- 置き場所: NaTsu の配布のリポジトリ（`src/updater.js:29` の `Kishi-Satoshi/natsu`）のリリース、タグ `stt-engine-whisper-vk-1.9.5-n1`、**prerelease・latest にしない**。NaTsu の自動更新は `releases/latest` だけを読み（`src/updater.js:30`）、札は `natsu-v<版>` の形だけを受け（`:43`）、資産は `natsu-src-*.zip` だけを受ける（`:41`）。`get-installer.ps1` も `releases/latest` か `natsu-v<版>` だけを読む（`:97`・`:100`）。GitHub の `releases/latest` は prerelease と draft を返さない。だから利用者の更新には混ざらない。
- workflow の artifact だけにしない理由: artifact は GitHub にログインしないと落とせず、既定で 90 日で消える。会社の PC のスクリプトから、版と SHA-256 で固定した URL で落とせるのはリリースの資産。
- 道具は今の取り込みと同じく `github.com` のリリースから取る（NaTsu の更新と同じ所なので、Zscaler の後ろで通ることが分かっている）。

| `cer.js` | CER（編集の距離 ÷ 参照の文字数）。両方を NFKC・小文字・「文字と数字」だけにして比べる。参照の行の頭の時刻 `[m:ss]` と札「自分:」「相手:」を外し、比べる音声の長さで参照を切る。数だけを出す。A0 とのずれにも使う |

| `README.md` | 持ち主への手順（短く） |

### 2 巡目で直した道具の所（2026-10-27）

- **2段にした:** `-Step 1`（既定。A0・D・Dn）と `-Step 2`（A1・A6・A4・B・C。`-Extra` で G）。A0 はどちらの段でも元で、測り済みなら測り直さない。`-Only` は段に関係なく、書いた記号だけ（知らない記号は止める）。
- **D・Dn の取得:** ピン `whisperVkZip`（NaTsu のリリースの prerelease の URL・大きさ・SHA-256）。CI で作って値を写すまでは `Size = 0`・`Sha = ""` で、そのあいだ D・Dn は測らない（段1 は止まる）。CPU 版とは別のフォルダ（`whisper-vk`）に開く。同じフォルダに置くと、CPU 版の exe も `ggml-vulkan.dll` を読んで GPU を使ってしまう（`ggml_backend_load_all` は exe のフォルダの DLL を全部読む）。
- **GPU を本当に使ったかの見分け:** whisper の回は `-np` を外し、標準エラーの記録を一時のファイルに受けて、`using Vulkan`・`failed to initialize Vulkan`・`DeviceLost` の行で「GPU」「CPU に戻った（…）」「GPU で落ちた」を決める（失敗の行を先に見る。whisper は「using」を出してから初期化するため）。一度でも GPU を使えなければ、残りの D・Dn は飛ばす。記録の行はパス（利用者名）を含むので、表に入れず、`log.txt` に残す誤りの行もパスを `<path>` に替える。whisper-cli の画面の出力（文が入る）は回の終わりに消す。
- **GPU の使用率:** 2 秒ごとに WMI の `Win32_PerfFormattedData_GPUPerformanceCounters_GPUEngine` から、候補のプロセス（`pid_<番号>_…`）のエンジンの使用率を、種類（3D・Compute など）ごとに足して、いちばん忙しい種類を取る。読めない PC では空。全部の候補で測る（測りの手間を候補の間でそろえる）。
- **A0 とのずれ:** D・Dn（と段2 の候補）の文を、同じ音声の A0 の文と `cer.js` で比べた数。参照が無くても出る。`-CerOnly` でも作り直す。
- **表に足した列:** GPU（使えたか）・GPU 平均/最大%・A0 とのずれ%。頭に GPU の名前とドライバの版・日付（`Win32_VideoController` の Intel の行）。D・Dn に GPU を使えなかった回があれば、太字の注意を1行。

### 流れ

1. **取得と照らし。** 段の候補に要るものだけを `%LOCALAPPDATA%\natsu-bench\stt` に落とし、SHA-256 を照らす（続きから取る・2回まで取り直す・空きを先に見る）。turbo と VAD は、NaTsu が取り込んだもの（`%LOCALAPPDATA%\natsu\engine\models`）が同じ中身なら相対のパスで借りる。段1 で落とすのは whisper.cpp の CPU 版（8.9MB）と Vulkan 版（約 22MB）だけ。
2. **音声。** WAV を1本ずつ窓へドラッグ → `wavprep.js` が m1〜m3 に直す（頭から 10 分）。元の名前は使わない。
3. **参照。** NaTsu で同じ会議の文字起こしの［コピー］→ メモ帳に貼って保存（`ref\m1.txt`…）。後からでもよい（`-CerOnly`）。
4. **測り。** NaTsu を終了してもらい（`whisper-server` が動いていれば待つ）、候補 × 音声ごとに: 見張りを起こして 30 秒の「静か」→ 候補を起こし、すぐ優先度を付ける → 1 秒ごとに候補の CPU 時間と最大のワーキングセット、2 秒ごとに PC 全体の CPU と候補の GPU の使用率 → 終わったら見張りを止め、GPU を使えたかを記録から読み、候補の文を `raw\` に置き、CER と A0 とのずれを出し、結果のファイル1つを置く。
5. **表。** `results\summary.md`・`summary.csv` に数だけ。PC の型番・論理コア・メモリ・Windows の版・GPU の名前とドライバの版は入れる。利用者名・パス・ファイルの名前・会議の文は入れない。

### 候補の動かし方（NaTsu の頼み方に合わせる）

- **whisper（A・B・D）:** zip の `whisper-cli.exe` を、1本の音声の 75 秒の区切り（`c001.wav`…）を全部 `-f` で渡して1回起こす（モデルを読むのは1回）。`-l ja -sns --vad -vm <VAD> -bs 1 -bo 2 -otxt -t <N>`（Dn は `-nfa` も）。`-bs 1 -bo 2` は whisper-server の既定（`examples/server/server.cpp:81`〜`:82`）に合わせるため（whisper-cli の既定はビーム探索 5 で、NaTsu より遅く出る）。flash attention は whisper-server も whisper-cli も既定で入（`server.cpp:106`・`cli.cpp:79`）。**認識ヒント（辞書・直前の文）は渡さない**（C・G に無いので、そろえる）。
- **sherpa-onnx（C・G）:** `sherpa-onnx-vad-with-offline-asr.exe --silero-vad-model=… --tokens=… --encoder=… --decoder=… --joiner=… --num-threads=<N> --decoding-method=greedy_search <full.wav>`（G は `--nemo-ctc-model=…`）。1本の音声で1回。
- **どれも** exe のフォルダを作業フォルダにし、モデルと音声は `..\models\…`・`..\wav\…` の相対パス（利用者名に日本語があっても引数は英数字だけ。RF1 と同じ扱い）。

### 音声の取り方（SQ4 の答えどおり）

NaTsu からは会議の音声を取り出せない（区間の WAV は文字になると消す。`src/main.js:3921`〜`:3923`）。だから **別に録る**: Windows の「サウンド レコーダー」の録音形式を WAV にし、対面の会議を、NaTsu をいつもどおりオンラインで録りながら同時に録る。音声と文は送らない・git に入れない。

### 参照の作り方（SQ3 の答えどおり）

同じ会議の NaTsu のクラウドの文字起こし（中継の `gpt-4o-transcribe`。`relay/config.mjs:20`）を、文字起こしのタブの［コピー］で写して使う。行の形は「[0:12] 自分: 文」（`src/renderer/app.html:2973`）。クラウドにも誤りがあるので、この CER は「クラウドとのずれ」で、候補どうしの**差**を見るのに使う。

### 測りで起きそうな失敗（Review Focus）

1. **NaTsu の whisper が並んで動く**（数が倍に乱れる）→ 測りの前に `whisper-server` が無いことを確かめ、あれば待つ。
2. **D が黙って CPU で動く**（`vulkan-1.dll` が無い・GPU の初期化に失敗）→ 記録の行と GPU の使用率の2つで見分け、表に「CPU に戻った」と書き、残りの D を飛ばす。
3. **D が途中で落ちる（`DeviceLost`）・文が崩れる** → 終了コードと記録の行で「GPU で落ちた」とし、Dn（flash attention を切る）の数と比べる。崩れは A0 とのずれ・長さの比で見る。
4. **会社の回線が NaTsu のリリースの資産や Hugging Face を止める・書き換える** → SHA-256 で止め、取得元のホスト名を画面に出して写してもらう。
5. **電池・熱で遅くなる**（ノート PC。GPU も同じ 15W の枠）→ 回ごとに電源の状態を表に残し、30 秒の静かな間を挟む。

- 2 巡目の `bench-stt.ps1` の直し: `tools/lib/ps1.js` の括弧と引用符の確かめ（0）。PS 7 だけの書き方（`?:`・`??`・`&&`・`-Parallel`）と `switch`・`[ValidateSet]` を使っていないこと。**PowerShell での構文の読みと通しは、今回の作業環境では PowerShell を入れられず、できなかった**（1 巡目は 7.4 で通した）。承認の後、道具を持ち主に渡す前に、PowerShell 7.4 で構文の読みと偽の候補の通し（GPU の行がある・無い・失敗の行がある記録を出す偽の whisper-cli で、3つの見分けと飛ばし）を行う。

## 決める線（SQ5 の答え「標準（おすすめ）」）

- **外す:** 終了コードが 0 でない回がある・長さの比が 0.8〜1.2 の外の音声がある・最大メモリが 2GB を越える。**D は、GPU を使えなかった回（「CPU に戻った」「GPU で落ちた」）が1つでもあれば外す**（案。GQ5）。
- **速さ:** 低い優先度・スレッド 4 で **RTF ≤ 0.3**（測りは静かな PC なので、会議中は 1.5〜2 倍に遅くなると見て、0.6 以下に収める）。**D が届くかは分からない**（#2542 の Iris Xe の数は RTF 約 0.46。古い版・別の旗の数）。
- **精度:** CER が A0 より **2 ポイント**より悪くならない。
- **重さ:** 候補の CPU 平均が PC の **40%** 以下で、仕事の時間の倍率が 1.5 以下。
- **選び方:** 段1 で D が全部の線を越えれば、D を入れる版の計画へ（段2 は測らない）。越えなければ段2 を測り、残ったものから CER の低い順、並べば CPU の少ない方。どれも残らなければ、A1（優先度だけ）と今の「遅い会議は会議の後に PC で」（0.9.4）で続け、持ち主と決め直す。D が線に届かないが A0 より明らかに速く文も正しいときの扱いは GQ4。

## 持ち主の試作から参考にしたこと（2026-10-27 の 2 巡目に読み直した。2026-10-17 の試作）

持ち主が渡した試作（`db-server.js`・`main.js`・`preload.js`・`state-store.js`・`README.md`・`package.json`）と、同じときに渡された第0b回 Task 0 の結果（`bench-E4B-cpu.md`）と `engine.log` 2つを、全部読み直した。試作は「DB 専用のプロセスと画面を MessagePort でつなぐ」最小の形で、文字起こしや GPU の道具ではないが、次の考え方を、測りの道具と GPU の「決まった後」の素描に使った。名前と値（命令の名前・欄の名前・間引きの秒数など）は持ち込まない。採るのは、Node・Electron の公式の資料か今の NaTsu のコードに同じ形があるものだけ（`natsu-design.md` の「全体を通して守ること」）。

## 決まった後（素描。組み込みは別の計画に書き、またソクラテス式の問答をする）

- **D（GPU）のとき:**
  - **ピン:** `engine-manifest.js` に、Vulkan 版の組を1つ足す（URL は NaTsu のリリースのタグ・大きさ・SHA-256・中のファイルの全部）。置き場所は版を含む別のフォルダ（`whisper-1.9.5-vk` など）。CPU 版の組は消さずに残す（戻り先）。CI の作り方は段1 のワークフローを、リリースの作り方として固める（`engine-manifest.js` の頭の「変えた commit は Windows の CI の engine-smoke が緑」も守る）。
  - **形の選び（その計画で問う）:** (a) 段1 と同じく全部を自分たちで作った組を使う。(b) 上流の b5454 の CPU 版はそのままにし、自分たちで作った `ggml-vulkan.dll` だけを別のフォルダに置いて、GPU のときだけ環境変数 `GGML_BACKEND_PATH` で読ませる（CPU に戻すときは変数を付けないだけ。上流の DLL と作りの道具が違うおそれは、CI の煙テストで見る）。
  - **CPU へ戻す:** whisper-server が GPU で落ちたら、`-ng` で起こし直してその会議は CPU で続ける（区間は今の「失敗した区間は残してやり直す」で失わない）。起動のときの印（上の試作の `EPHEMERAL` の考え）で、落ちたドライバの版では次から CPU。
  - **IT がドライバを更新したとき:** 起動のときにドライバの版（`Win32_VideoController`）を読み、前と違えば、短い音で GPU と CPU の答えを比べる確かめを1回して、合わなければその版では CPU にする（GQ6）。
  - **記録:** `engine.log` に「GPU で動いた（ドライバの版）／CPU に戻った（理由）」を1行。パスは書かない。
  - **設定:** 「計算の土台」= 自動（GPU を試し、だめなら CPU）・CPU の2つ。手で入れたパスの人（詳細設定）は今のまま。
  - **ヘルプ:** 「オフライン」の記事・INSTALL の取り込みの大きさ（約 22MB 増）・ライセンス（whisper.cpp と ggml は MIT のまま。Vulkan の実行の部品は配らない〔ドライバのもの〕）。
- **A（スレッド・優先度）・B（small）・C（ReazonSpeech）のとき:** 1 巡目の素描のまま（`spawn` の後の `os.setPriority`・スレッド数の既定の移し／`whisper-model` の1行の差し替え／組 `sherpa` と tar.bz2 を開く手段・エンジンの口・認識ヒントが使えない・ライセンスの写し）。D と一緒に入れるときは、D の CPU の残り（スレッド 4・BelowNormal）にも A の直しが効く。

## 持ち主への問い（選択式。おすすめを先頭に。理由と失うもの）

**GQ1. GPU はどの道で試しますか。**
- (a) **おすすめ:** whisper.cpp ＋ Vulkan を NaTsu の CI で作る（道 1）。理由: 今のモデル・今の頼み方のまま、足すのは約 13MB の DLL だけ。GPU が使えないと CPU に戻る仕組みが whisper.cpp にある。llama.cpp が同じ作り方で Windows の Vulkan 版を出している。失うもの: 自分たちで作った exe/DLL を持つ責任。Intel の iGPU で落ちる・文が崩れる報告がある（測りで見る）。
- (b) whisper.cpp ＋ OpenVINO（道 2）。理由: Intel が作った道具で、エンコーダーを iGPU で動かす。失うもの: 約 1.4GB 多く落とす・Python で変換する CI・速さの公開の数が無い。
- (c) sherpa-onnx ＋ DirectML（道 3）。理由: DirectX 12 はどの Windows の GPU でも動く。失うもの: 今のモデルではなくなる（ReazonSpeech）・DirectML は新しい機能が止まっている・配布物が無く作る必要がある。
- (d) GPU はやめて、段2（CPU の候補）だけを測る。理由: 自分たちで作るものを持たない。失うもの: 「遅い」と「重い」を両方軽くできるかもしれない道を見ない。

**GQ2. 自分たちで作った whisper.cpp（Vulkan 版）を、NaTsu のリポジトリのリリースに置いてよいですか。**
- (a) **おすすめ:** 置く。prerelease（latest にしない）で、タグ `stt-engine-whisper-vk-1.9.5-n1`。SHA-256 を計画と道具に固定する。理由: 会社の PC のスクリプトが、NaTsu の更新と同じ所から、固定の URL と SHA-256 で取れる。NaTsu の自動更新は latest と `natsu-v` の札しか読まないので混ざらない。失うもの: リリースの一覧に、NaTsu の版ではない項目が1つ見える（名前と説明で「測り用」と書く）。公開のリポジトリなら誰でも落とせる。
- (b) CI の artifact だけに置き、持ち主がブラウザで（GitHub にログインして）落として、窓へドラッグする。理由: リリースに何も足さない。失うもの: 手間が1つ増える。90 日で消える。道具が URL で照らせず、持ち主の手で落としたファイルの SHA-256 だけを照らす。
- (c) 置かない（GPU をやめる）。理由: 自分たちで作ったものを配らない。失うもの: GQ1 の (d) と同じ。

**GQ3. 作るワークフローを、どこに置いて動かしますか。**（GitHub の「手で起こす」ワークフローは、main にファイルが無いと起こせない）
- (a) **おすすめ:** 手で起こすときだけ動くワークフロー1つ（`stt-engine-vulkan.yml`。アプリと `ci.yml`・`release.yml` には触らない）を、小さな PR で main に入れる。持ち主が merge し、作り手が Run workflow で起こす。理由: 普段は動かず、作り直したいときだけ同じ手順で作れる。リリースの資産の作り方が記録に残る。失うもの: main に、アプリではないワークフローが1つ増える（merge には持ち主の言葉が要る）。
- (b) 決まったブランチ（例 `engine/whisper-vk`）へ push したときだけ動く形にし、main に入れない。理由: main を変えない。失うもの: そのブランチに push するたびに作り直す（約 20〜30 分の CI）。手で起こす形より誤って動きやすい。
- (c) 持ち主の PC で作る。理由: CI が要らない。失うもの: Vulkan SDK と Visual Studio を入れるのに管理者の権限が要り、会社の PC ではできない見込み。

**GQ4. D（GPU）が線に届かない、または文が違うときはどうしますか。**
- (a) **おすすめ:** 段2（CPU の候補）を同じ音声で測る。D は記録として残す。理由: 答え「測ってからまとめて直す」に合う。音声と A0 は測り直さないので、追加は約 1〜2 時間。失うもの: GPU の道は今回は閉じる。
- (b) 段2 の前に、D をもう1回だけ試す（新しい whisper.cpp のタグ〔出て2週間以上〕で作り直す）。理由: Intel 向けの直しが入っていれば変わるかもしれない。失うもの: CI と測りがもう1回（数日）。A0 と whisper の版がずれる。
- (c) 速さ（RTF）だけが届かず、A0 より明らかに速く文も正しいなら、D を「選べる設定」として入れる。理由: 今より確かに軽い。失うもの: 線を下げることになる。会議中に追いつかないことがある（今の「遅い会議は会議の後に PC で」で受ける）。

**GQ5. GPU の文が正しいかを、どう判じますか。**
- (a) **おすすめ:** SQ5 の線（クラウドとの CER が A0 の +2 ポイントまで・長さの比 0.8〜1.2）に加え、D の全部の回で GPU を使えていて落ちていないこと。A0 とのずれは表に出すが、線にはしない。理由: GPU は計算の細かい違いで言葉が少し変わるのはふつうで、本当に悪いかはクラウドとの比べで分かる。失うもの: 「CPU と同じ文」は約束しない。
- (b) (a) に加えて、A0 とのずれが 10% 以下。理由: 崩れた文をより早く見つける。失うもの: 正しいが言い回しの違う文でも外しうる。
- (c) A0 とのずれだけで判じる（参照を使わない）。理由: 参照の手間が要らない。失うもの: A0 の誤りを「正しい」とみなす。

**GQ6. 入れた後に、会社の IT が Intel のドライバを更新したらどうしますか。**
- (a) **おすすめ:** NaTsu が起動のときにドライバの版を読み、変わっていたら短い音で GPU と CPU の答えを比べる確かめを1回して、合わない・落ちるならその版では CPU に戻す（知らせを1つ出す）。理由: whisper.cpp のコードにも「この版の Intel の Windows のドライバでは落ちる」という分かれ道があり、版で動きが変わる。利用者の手は要らない。失うもの: ドライバが変わった後の最初の起動が数秒〜数十秒遅れる。作る量が増える。
- (b) GPU は既定で切り、使いたい人が設定で入れる。理由: 作る量が少ない。失うもの: 50 人のほとんどが GPU を使わず、軽くならない。
- (c) IT にドライバの版を固定してもらう。理由: NaTsu の側は簡単。失うもの: IT への頼みごとが要る。セキュリティの更新を止めることになりうる。

**GQ7. 測りでの D の形はどれにしますか。**
- (a) **おすすめ:** スレッド 4・BelowNormal（入れるときの形）で3本、flash attention を切った Dn を1本。理由: 入れたときの「重さ」がそのまま分かる。#3537 の「flash attention を切ると落ちない」も1本で見られる。失うもの: A0（スレッド 10・ふつう）との差に、GPU の効き目とスレッド・優先度の違いが混ざる。
- (b) A0 と同じスレッド 10・ふつうの優先度で3本。理由: GPU だけの効き目が分かる。失うもの: 入れるときの重さは分からない（もう1回測る）。
- (c) (a) と (b) の両方。理由: 両方分かる。失うもの: 測りが約 30〜60 分延びる。

## 文書とコードの食い違い（見つけたもの）

1. **（1 巡目の計画の誤り）「上流の配布物を固定する決まりから外れる」:** 1 巡目の計画は、D を外した理由に「今の『上流の配布物を版と SHA-256 で固定する』決まり（`engine-manifest.js` の頭）から外れる」と書いた。`engine-manifest.js` の頭（`:7`〜`:17`）の決まりは「URL は版を固定する。GitHub はリリースのタグ、Hugging Face は 40 桁の commit」「latest・main・api.github.com は使わない」で、**上流のものに限るとは書いていない**。自分たちのリリースのタグと SHA-256 で固定すれば、書かれた決まりには合う（それでも「自分たちで作ったものを配る」ことは新しい決めなので GQ2 で問う）。この計画で直した。
2. **NaTsu の `engine.log` には、whisper がどの計算の土台で動いたかが残らない:** whisper-server の標準出力は捨て、標準エラーは落ちたときの3行だけ（`src/main.js:1048`〜`:1072`）。持ち主の `engine.log` 2つにも `load_backend` の行は無い。今は CPU 版しか無いので困らないが、GPU を入れるなら1行残す（「決まった後」）。
3. **`ggml_backend_load_all` は exe のフォルダの `ggml-*.dll` を全部読む:** アプリの取り込み（`engine-install.js`）はマニフェストに書いたファイルしか置かないので、今は問題ない。ただし、詳細設定の「手で入れたパス」や `setup-local-engine.ps1` で入れたフォルダに誰かが Vulkan の DLL を置くと、NaTsu は知らないまま GPU を使う。ヘルプの「手で入れる」に注を足すかは、D を入れる計画で決める。
4. **第0b回 Task 0 の Vulkan の比べの数が残っていない:** 0b の計画（`2026-10-17-0b.md` の Task 0）は、llama.cpp の Vulkan 版で Iris Xe と CPU を比べることにしていたが、リポジトリに残る結果は CPU の割り当ての失敗（`bench-E4B-cpu.md`）だけで、Vulkan の数は無い。この計画の段1 が、この機種での GPU の最初の数になる。
5. 1 巡目に挙げた食い違い（`README.md:519`・`INSTALL.md:348` の「スレッド数を上げる」・`setup-local-engine.ps1:220` の古いピン・区切りは 75 秒だけではない・`INSTALL.md:211` の常駐のメモリ・`engine-manifest.js:31` の注は正しい）は、そのまま残る（この計画ではアプリの文書を直さない。決まった後の版で直す）。
