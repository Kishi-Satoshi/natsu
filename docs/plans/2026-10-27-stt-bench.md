## 持ち主の頼み（2026-10-27。そのまま）

「現在、ローカルの文字起こしで使っているモデルは何ですか？重くてつらいので、別のものに入れ替えたいですが、候補を出してもらえると助かります。」

つらいのは2つ: **「文字になるのが遅い」** と **「PC 全体が重くなる」**。取り込みの約 0.6GB は気にしていない。候補を出したときの答えは「候補をあなたの PC で測ってから決める（おすすめ）」。出した候補は ① ReazonSpeech k2 v2（sherpa-onnx）・② whisper small・⑤ 今のモデルを Iris Xe（Vulkan）で。

## 目的・方針

- **目的:** 持ち主の PC（Core i5-1335U〔10 コア・12 スレッド。P コア 2・E コア 8〕・16GB・Iris Xe・Windows 11 25H2・Zscaler。配る 50 台も同じ機種）で、文字起こしの候補を **同じ音声・同じ測り方** で比べ、2つのつらさのどちらがどれだけ軽くなり、精度をどれだけ失うかを数で見せる。決めるのは持ち主。
- **方針:**
  - 測るのは持ち主の PC だけ（作業環境は Linux で、i5-1335U の E コアと Iris Xe を真似できない）。持ち主はスクリプトを1つ動かし、数だけの表を貼って返す。
  - 音声と文字はその PC から出さない。表には数だけを書く（会議の文・ファイルの名前・利用者のパスを入れない）。
  - 落とすものは全部、版か commit で固定した URL と、大きさ・SHA-256 で照らす（`src/engine-manifest.js` と同じ決まり）。置き場所は `%LOCALAPPDATA%\natsu-bench\stt`（C ドライブ直下は会社の PC が止める。第0b回 Task 0 と同じ）。
  - NaTsu の設定・取り込んだエンジン・議事録には触らない。NaTsu が取り込んだモデルは、同じ中身（SHA-256）なら読むだけで使う（0.6GB を落とし直さない）。
  - 第0b回 Task 0（`tools/bench-summarizer.ps1`。要約のモデルの比べ）の形を引き継ぐ: 続きから取れる取得・2回まで取り直す照らし・画面の案内どおりに Enter・NaTsu を測り中だけ終了・結果は数だけ。

### 流れ

1. **取得と照らし。** 候補に要るものだけを `%LOCALAPPDATA%\natsu-bench\stt` に落とし、SHA-256 を照らす（続きから取る・2回まで取り直す・空きを先に見る）。turbo と VAD は、NaTsu が取り込んだもの（`%LOCALAPPDATA%\natsu\engine\models`）が同じ中身なら相対のパスで借りる。sherpa-onnx の tar.bz2 は Windows の `System32\tar.exe` で開く（開けなければエクスプローラーの［すべて展開］へ案内）。どれも Zscaler の後ろで NaTsu の取り込みがすでに使っている所（`github.com` のリリース・`huggingface.co`）から取る。
2. **音声。** WAV を1本ずつ窓へドラッグ → `wavprep.js` が m1〜m3 に直す（頭から 10 分。`-MaxMinutes`）。元の名前は使わない。
3. **参照。** NaTsu で同じ会議の文字起こしの［コピー］→ メモ帳に貼って保存（`ref\m1.txt`…）。後からでもよい（`-CerOnly`）。
4. **測り。** NaTsu を終了してもらい（`whisper-server` が動いていれば待つ）、候補 × 音声ごとに: 見張りを起こして 30 秒の「静か」→ 候補を起こし、すぐ優先度を付ける → 1 秒ごとに候補の CPU 時間と最大のワーキングセット、2 秒ごとに PC 全体の CPU（`Win32_PerfFormattedData_PerfOS_Processor`。カウンターの名前は日本語の Windows で訳されるので `Get-Counter` は使わない）→ 終わったら見張りを止め、候補の文を `raw\` に置き、CER を出し、結果のファイル1つを置く。A1・A6・A4 は 1 本目の音声だけ（スレッドと優先度は速さと重さしか変えないので、精度は A0 で見る）。
5. **表。** `results\summary.md`・`summary.csv` に数だけ。PC の型番・論理コア・メモリ・Windows の版は入れる（50 台が同じ機種かの確かめ）。利用者名・パス・ファイルの名前・会議の文は入れない。

### 候補の動かし方（NaTsu の頼み方に合わせる）

- **whisper（A・B）:** zip の `whisper-cli.exe` を、1本の音声の 75 秒の区切り（`c001.wav`…）を全部 `-f` で渡して1回起こす（モデルを読むのは1回）。`-l ja -sns --vad -vm <VAD> -bs 1 -bo 2 -otxt -np -t <N>`。`-bs 1 -bo 2` は whisper-server の既定（`examples/server/server.cpp:81`〜`:82` の `best_of = 2`・`beam_size = -1`。ビーム探索なし）に合わせるため。whisper-cli の既定はビーム探索 5（`examples/cli/cli.cpp:44`〜`:45` と `src/whisper.cpp:6187`）で、そのままだと NaTsu より遅く出る。`no_context` は既定で真（`src/whisper.cpp:6099`）。温度の上げ（0.2 刻み）は両方とも同じ。**認識ヒント（辞書・直前の文）は渡さない**（C・G に無いので、そろえる。持ち主の辞書の言葉を道具に持たせない）。
- **sherpa-onnx（C・G）:** `sherpa-onnx-vad-with-offline-asr.exe --silero-vad-model=… --tokens=… --encoder=… --decoder=… --joiner=… --num-threads=<N> --decoding-method=greedy_search <full.wav>`（G は `--nemo-ctc-model=…`）。1本の音声で1回（モデルを読むのは1回）。入力は「モノラル・16 ビットの PCM の WAV」（v1.13.8 の `sherpa-onnx-vad-with-offline-asr.cc` の使い方の文）なので、`wavprep.js` の直した WAV を渡す。出る行は「開始 -- 終わり: 文」。
- **どちらも** exe のフォルダを作業フォルダにし、モデルと音声は `..\models\…`・`..\wav\…` の相対パス（利用者名に日本語があっても引数は英数字だけ。whisper が英数字以外のパスを読めない RF1 と同じ扱い）。

### 測る数（表の列）

| 数 | 測り方 | 何の目安か |
| --- | --- | --- |
| 処理秒・**RTF** | 起こしてから終わるまでの壁の時計 ÷ 音声の秒（モデルを読む時間も入る。1本に1回） | 「文字になるのが遅い」。1 より小さければ追いつく |
| 候補の CPU 平均・最大%・使ったコア数 | 候補のプロセスの CPU 時間の増え ÷ 経った時間 ÷ 論理コア数（平均は終わりの CPU 時間から） | 「PC 全体が重い」の元 |
| PC 全体の CPU 平均・最大% | 2 秒ごとの `_Total` | 同じ（ほかのプロセスも含む） |
| 最大メモリ MB | 候補のプロセスの最大のワーキングセット | 16GB の PC で Teams・ブラウザと並べられるか（INSTALL の「whisper 常駐 0.8〜1.2GB」の確かめにもなる） |
| 時計の遅れ p95・最大（静か→測り中） | `probe.js`（ふつうの優先度）。25 ミリ秒ごとに起きる約束の遅れ | ほかのアプリの返りのもたつき |
| 仕事の時間の倍率 | `probe.js` の決まった計算の時間の中央値（測り中 ÷ 静か） | ほかのアプリが CPU を取れるか |
| **CER%**・長さの比・句点の数 | `cer.js`。長さの比 = 候補 ÷ 参照（0.8 より下は抜け落ち、1.2 より上は繰り返しの暴走の目安）。句点の数は候補の元の文の「。」の数 | 精度。NaTsu の文ごとの行は句点に頼るので、句点を打つかも見る |
| 終了コード・電源 | — | 失敗した回・電池で動いた回を見分ける |

### 音声の取り方（SQ4）

NaTsu からは会議の音声を取り出せない: 区間の WAV は文字になると消す（`src/main.js:3921`〜`:3923` の `settleSegment`。残すのは失敗した区間だけ）。会議を丸ごと残す設定も無い。だから **別に録る**: Windows の「サウンド レコーダー」の録音形式を WAV にし、NaTsu をいつもどおりオンラインで録りながら同時に録る（対面の打ち合わせ、またはスピーカーで鳴らす Web 会議）。サウンド レコーダーはマイクだけを録るので、ヘッドセットの Web 会議では相手の声が入らない。録った WAV は `wavprep.js` が 16kHz・モノラルに直す（48kHz・ステレオ・24 ビット・小数のどれでもよい）。音声と文は送らない・git に入れない（`.gitignore` と `test/repo.test.js` の「モデル・音声・ログなどの生成物が追跡されていない」がもう止める）。

### 参照の作り方（SQ3）

- **(a) おすすめ:** 同じ会議の NaTsu のクラウドの文字起こし（中継の `gpt-4o-transcribe`。`relay/config.mjs:20`）を、文字起こしのタブの［コピー］で写して、そのまま使う。行の形は「[0:12] 自分: 文」（`src/renderer/app.html:2973`）。`cer.js` が時刻と札を外し、比べる長さ（頭の 10 分）で切る。
- クラウドの文字起こしにも誤りがあるので、この CER は「クラウドとのずれ」。候補どうしの**差**を見るのに使う（同じ参照なので、ずれは全候補に同じだけ乗る）。2つの流れ（自分・相手）の会議では行の並びが時刻順になり、マイク1本の録音と言葉の順が少し違うことがあるが、これも全候補に同じ。
- 確かめたいときは、1本の 5 分だけを手で直した参照を足す（(b)）。

### 時間の目安

10 分 × 3 本で約 2〜3 時間（A0 は音声の約 2 倍の時間。A1・A6・A4 は1本だけ。B と C は短い見込み）。回ごとに 30 秒の「静か」を挟む（冷ます間にもなる）。途中で止めても、次は続きから。電源につなぎ、PC を触らずに置いてもらう（昼休み・夕方）。

### 測りで起きそうな失敗（Review Focus）

1. **NaTsu の whisper が並んで動く**（数が倍に乱れる）→ 測りの前に `whisper-server` が無いことを確かめ、あれば待つ。
2. **電池・熱で遅くなる**（ノート PC）→ 回ごとに電源の状態を表に残し、30 秒の静かな間を挟む。電池なら知らせる。
3. **会社の回線が sherpa-onnx の取得元（`release-assets.githubusercontent.com`）や Hugging Face の配信（xet）を止める・書き換える** → SHA-256 で止め、取得元のホスト名を画面に出して写してもらう。
4. **この PC の `tar.exe` が bzip2 を開けない**（Windows の版による）→ 開けなければ止めて、エクスプローラーで開く手順を出す（C を入れるときに取り込みでも同じ問題が出るので、ここで分かることにも意味がある）。
5. **参照と音声の頭がずれる・長さが違う** → 頭の時刻で参照を切る。ずれは全候補に同じなので差の比べは保たれる。長さの比が全候補で 0.8 を切るなら、参照の取り違えを疑う。

### 確かめたこと（この作業環境で）

- `wavprep.js`: 48kHz・ステレオ・24 ビット（200 秒）と 44.1kHz・ステレオ・32 ビット小数（EXTENSIBLE）と 16kHz を作って通した。75 秒ずつに切れる。1kHz と 10kHz を混ぜた音から、16kHz にした後の 1kHz は 0.400 のまま、10kHz の折り返し（6kHz）は 0.0001 で、折り返しが入らないことを見た。10 分の 48kHz の音声で約 10 秒。
- `cer.js`: 時刻と札を外す・頭の N 秒で切る・句読点と空白を外すことを、例の文で見た（1文字違いで 2.9%）。編集の距離は 2 万字 × 2 万字で約 3 秒。
- `probe.js`: 静かと負荷を分けて数えることを見た。
- `bench-stt.ps1`: PowerShell 7.4 の構文の読み（エラー 0）と `tools/lib/ps1.js` の括弧の確かめ（0）。偽の候補（CPU を回して文を書くだけの台本）と偽の NaTsu.exe（Node）で、測り・CER・結果のファイル・表・読めない結果の退けを Linux の PowerShell 7.4 で通した。**Windows PowerShell 5.1 と本物の whisper-cli・sherpa-onnx では動かしていない**（作業環境が Linux で、落とした exe を動かすことは止められている）。PS 7 だけの書き方（`?:`・`??`・`&&`・`-Parallel`）は使っていない。

## 決める線（SQ5 で持ち主が決める。下は案）

- **外す:** 終了コードが 0 でない回がある・長さの比が 0.8〜1.2 の外の音声がある・最大メモリが 2GB を越える。
- **速さ:** 低い優先度・スレッド 4 で **RTF ≤ 0.3**（測りは静かな PC なので、会議中（Teams の映像など）は 1.5〜2 倍に遅くなると見て、0.6 以下に収める）。
- **精度:** CER が A0 より **2 ポイント**より悪くならない（参照がクラウドなので、比べるのは A0 との差）。
- **重さ:** 候補の CPU 平均が PC の **40%**（12 スレッドのうち約 5）以下で、仕事の時間の倍率が 1.5 以下。
- **選び方:** 残ったものから CER の低い順、並べば CPU の少ない方。どれも残らなければ、A1（優先度だけ）と今の「遅い会議は会議の後に PC で」（0.9.4）で続け、持ち主と決め直す。

## 決まった後（素描。組み込みは別の計画に書き、またソクラテス式の問答をする）

- **A（スレッド・優先度）だけのとき:** `spawn` の後に `os.setPriority`（Node の標準。依存を足さない）。スレッド数の既定の式を変えるなら、前の既定（10）の人を新しい既定へ移す（今の `migrateOldThreads` と同じ形。手で決めた数は変えない）。ヘルプと INSTALL の「スレッド数を上げる」を直す（下の食い違い 1）。テスト: 引数の `-t`・優先度を付ける1行・移し。
- **B（small）のとき:** `engine-manifest.js` の `whisper-model` の1行（URL・大きさ・SHA-256・置き場所）を差し替える。前のモデルの片付けと「新しい組がそろうまで前の組を使う」は今の取り込みの仕組み（第0b回）のまま。遅い PC の覚え（`local-pace.json`）はモデルの名前と大きさで分けているので、自然に測り直しになる。画面とヘルプの大きさの文（約 0.6GB → 約 0.3GB）。
- **C（または G）のとき:**
  - **ピン:** `engine-manifest.js` に組 `sherpa`（エンジンの tar.bz2・モデル4つ・VAD）。今の取り込み（`src/engine-install.js`）は zip しか開けない（`zipread` だけ: `src/engine-install.js:60`）ので、tar と bzip2 を開く手段が要る: Windows の `System32\tar.exe` を呼ぶ／依存なしの bzip2 の読み手を書く、のどちらか（その計画で問う）。MT 版なので Visual C++ ランタイムの確かめ（RF4）は要らない。
  - **エンジンの口（アダプター）:** 区間の WAV を渡して `{ text, segments[{start, end, text}] }` を返す口を1つにし、whisper（今の HTTP）と sherpa を並べる。sherpa は常駐の `sherpa-onnx-offline-websocket-server.exe`（モデルを読むのは1回。Node 24 の標準の WebSocket でつなぐ）か、区間ごとに `vad-with-offline-asr` を起こす（区間ごとにモデルを読み直す。測りで読む時間が分かる）か、を測りの数で決める。別のプロセスにし、優先度を付ける（試作の「重い仕事は別のプロセス」）。
  - **合わせて直す所:** 遅い PC の速さの式（`PACE_WINDOW_MS` の 30 秒の窓は whisper だけの話）・時間切れの式（`localTimeoutMs`）・文ごとの行（whisper の `verbose_json` の代わりに VAD の区切りの時刻）・認識ヒントを渡さない（辞書は文字にした後の置き換えだけ効く）。
  - **設定:** 「文字起こしのエンジン」（whisper・sherpa の決まった値だけ。知らない値は既定に戻す。試作の `SCHEMA`）。手で入れたパスの人（詳細設定）は今の whisper のまま。
  - **今の利用者の移し:** 次の起動で新しい組を取り込み、照らし終えたら切り替え、古い 574MB は片付ける（取り込みの約束どおり、そろうまでは前の組）。持ち主1人の今は自動、50 人に配る前は知らせの文を問う。
  - **オフラインのとき:** 今と同じ（PC の中だけで文字起こし）。クラウドの側は変えない。
  - **ヘルプ:** 「オフライン」の記事・INSTALL の取り込みの大きさと常駐のメモリ・ライセンスの写し（Apache-2.0 が2つ・onnxruntime の MIT・G なら CC-BY-4.0 の名前の表示・ReazonSpeech のコーパスの注）。

## 持ち主への問い（選択式。おすすめを先頭に。理由と失うもの）

**SQ1. 測る候補はどれにしますか。**
- (a) **おすすめ:** A0・A1・A6・A4・B・C（6 つ）。理由: 2つのつらさを分けて見られる（A は重さだけ、B・C は速さと重さ）。持ち主の挙げた ①② を全部測れる。失うもの: G（parakeet）の数は出ない。
- (b) (a) に G（parakeet-tdt_ctc-0.6b-ja）を足す。理由: 句読点つきで精度の評判が高い。失うもの: 約 0.66GB 多く落とし、測りが約 30 分延びる。モデルカードの無い変換を使う。
- (c) A だけ（A0・A1・A6・A4）。理由: 30 分ほどで済み、入れ替えずに軽くできるかが分かる。失うもの: 「文字になるのが遅い」を直す候補の数が出ない。

**SQ2. 安い直し（優先度とスレッド数）を、測りの前に 0.13.x で入れますか。**
- (a) **おすすめ:** 優先度（BelowNormal）だけを先に、小さな計画で入れる。スレッド数は測りの後。理由: 優先度はほかのアプリが忙しいときだけ whisper を後回しにするので、PC が空いているときの速さは変わらず、「PC 全体が重い」に効く見込み。1 行で戻せる。失うもの: 会議中に Teams などが CPU を使うと、遅い会議（会議の後に PC で）に入りやすくなる。A1 の数を見る前に決めることになる。
- (b) 測りが済むまで何も変えない。理由: 数を見てからまとめて決められる。失うもの: 測りと決めの間（数日）、今の重さのまま。
- (c) すぐ両方（スレッド 4・BelowNormal）。理由: 重さは一番軽くなる。失うもの: 今でも追いついていない文字起こしが、さらに遅くなる見込み（「文字になるのが遅い」が悪くなる）。

**SQ3. 精度の比べの元（参照）はどれにしますか。**
- (a) **おすすめ:** 同じ会議の NaTsu のクラウドの文字起こしを、そのまま。理由: ［コピー］して貼るだけで、全部の音声で使える。候補どうしの差は正しく出る。失うもの: クラウドの誤りも「ずれ」に数えるので、本当の誤り率ではない。
- (b) (a) に加えて、1 本の 5 分だけを手で直した参照も作る。理由: 本当の誤り率の目安も1つ取れる。失うもの: 持ち主の手間（約 20〜30 分）。
- (c) 全部を手で直す。理由: いちばん確か。失うもの: 10 分 × 3 本で数時間の手間。

**SQ4. 音声はどう録りますか。**
- (a) **おすすめ:** 対面の打ち合わせを、サウンド レコーダー（WAV）と NaTsu（オンライン）で同時に録る。理由: 本物の会議の話し方で、参照も同時にできる。失うもの: 社外秘の少ない打ち合わせを選ぶ必要がある。
- (b) Web 会議をスピーカーで鳴らし、同じく同時に録る。理由: 相手の声も入る。失うもの: スピーカーの音をマイクで拾うので、音がやや悪い（全候補に同じ）。周りに声が聞こえる。
- (c) 用意した台本を自分で読み上げて録る。理由: 社外秘を気にしなくてよい。失うもの: 会議らしい言いよどみ・重なりが無く、差が出にくい。

**SQ5. 決める線はどれにしますか。**
- (a) **おすすめ:** RTF ≤ 0.3・CER は A0 の +2 ポイントまで・候補の CPU 平均 ≤ 40%（上の「決める線」）。理由: 会議中の負荷で遅くなっても追いつき、精度をほとんど失わない。失うもの: B（small）は精度で外れる見込みが高い。
- (b) RTF ≤ 0.5・CER は +5 ポイントまで。理由: 軽さを優先し、少しの誤りは許す。失うもの: 名前や数の誤りが目に見えて増えうる。
- (c) 精度優先: CER が A0 以下のものだけ。理由: 今の質を落とさない。失うもの: どれも残らず、A1（優先度だけ）で終わる見込み。

**SQ6. D（Iris Xe の GPU・Vulkan）はどうしますか。**
- (a) **おすすめ:** 今回は外す。理由: whisper.cpp の公式の Windows の Vulkan 版が無く、上流の配布物を固定する決まりから外れる。失うもの: GPU を使えば CPU が空く可能性を見られない。
- (b) NaTsu の Windows の CI で whisper.cpp を Vulkan 付きで作る計画を別に立てる。理由: CPU をほとんど使わずに済むかもしれない。失うもの: 作る仕組み・署名・会社の PC のドライバの差を自分たちで持つことになる（大）。

**SQ7. 音声の長さと本数はどれにしますか。**
- (a) **おすすめ:** 10 分 × 3 本（約 2〜3 時間）。理由: 話し方の違う会議を3つ見られ、1回の昼休み＋α で済む。失うもの: 長い会議の後半（疲れた声・話題の変わり）は入らない。
- (b) 30 分 × 2 本（約 5〜6 時間）。理由: 長い会議に近い。失うもの: 1日がかり。
- (c) 5 分 × 3 本（約 1 時間）。理由: すぐ済む。失うもの: 数がぶれやすい。

## 文書とコードの食い違い（見つけたもの）

1. **「スレッド数を上げる」の案内:** `README.md:519`（高速化の1）と `INSTALL.md:348`（「文字起こしが遅い」）は「スレッド数を上げる（既定は論理コア数 − 2）」と案内する。既定はもう 12 スレッドのうち 10 で、上げられるのは 12 まで。持ち主の `engine.log` では `-t 10` で 1.7〜2.1 倍で、上げても追いつく見込みは薄く、「PC 全体が重い」を悪くする。この計画の結果で書き直す（決まった後の A）。
