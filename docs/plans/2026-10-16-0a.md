**回の名前:** 第0a回（0.1.0）— 名前・ロゴ・保存先・設定の整理・CI（設計書 :71, :147）

**目的:** Listener を NaTsu という別のアプリとして新しく入れられる 0.1.0 を、Linux と Windows の CI が緑の commit から、タグ `natsu-v0.1.0` で出す（設計書 :64, :151-158）。エンジンの自動取り込み（R7）は第0b回なので、ここでは作らない（設計書 :103）。

**方針（アーキテクチャ）:**
- **名前の決め手は package.json の3か所。**
  - top-level の `name` が `app.getName()` になり、そこから `userData` が決まる（electron 31.3.0 `electron.d.ts:1205-1213`）。
  - `build` の中身は、配る package.json から消える（app-builder-lib 24.13.3 `out/fileTransformer.js:58`）。だから `build.productName` は exe の名前とインストール先（`out/targets/targetUtil.js:38-39`、`templates/nsis/multiUser.nsh:30`）を決めるだけで、`userData` には効かない。
  - `build.appId` は NSIS の GUID になる（`out/targets/nsis/NsisTarget.js:147`）。変えると Listener の上書きではなく、別のアプリとして入る。
  - そこで `name: "natsu"`・`build.productName: "NaTsu"` とし、top-level の `productName` は足さない。こうすると `userData` は `%APPDATA%\natsu` になる（設計書 :153 の「どちらが効くか」への答え）。
  - 上の3つの出典は、調査者が落とした写しで確かめた（スクラッチパッドの `dl-electron` / `dl-abl`）。
- **自動更新で入れ替わるのは `src/` だけ**（updater.js:257-259）。タグの形 `natsu-v<x.y.z>` と資産の名前 `natsu-src-*.zip` は、updater.js と release.yml と make-release.ps1 で同じにし、テストで突き合わせる。
- **データの置き場所は `<userData>/data` だけにする。** `store.init` を1引数に戻す。設定キー `dataDir` は読みもせず、書き戻しもしない。
- **設定画面の id は1つも変えない**（設計書 :184）。変えるのは包む枠だけ（カード・`<details>`）。ゲートは、id のある要素が `div.row` などクラスのある枠から出ると BLOCK する（tools/risk.js:45-58, :80-95）。だから枠からは出さない。
- **CI:** `ci.yml` を新しく作り、release.yml から `workflow_call` で呼ぶ。`release` ジョブには `needs: ci` を付ける。こうして、その commit で両方の OS が緑のときだけリリースする（設計書 :151, :429）。

- Electron 31（package.json:20）と electron-builder 24（package.json:21）。どちらも今ある devDependencies。

**この回で足す決まり**

- **Task 4 から Task 13 の commit までの間は、手元のソースでアプリを起動しても、更新の告知を当てない。**

  - **ステップ（この順）:**
    1. `git config --global core.autocrlf false`
    2. `actions/checkout@v4`。`fetch-depth: 0`（gate.test.js:53-80 が古いコミットを読む）。
    3. `actions/setup-node@v4`。`node-version: '22'`（package.json:10 の glob は Node 21 以上が要る）。
    4. **テスト**（`shell: bash`）: `npm test` の出力から `# skipped N` を読む。許すのは Linux で 0、Windows で 1（stage3.infra.test.js:18, :107 の sh の実走）。超えたら `::error::` で止める。
    5. **ゲート**（`shell: bash`）: 基準 `BASE` を決める。PR なら `git merge-base "origin/$BASE_REF" HEAD`、push なら `github.event.before`。そのうえで `node tools/risk.js --base "$BASE" --head HEAD` を回す（素の `npm run gate` は作業ツリーとしか比べないので、CI では必ず 0 件になる: risk.js:307, :320）。
       - **使えない基準:** 空、0 だけの並び（`[[ "$BASE" =~ ^0+$ ]]`）、履歴に無い（`git cat-file -e "$BASE^{commit}"` が失敗する）、HEAD と同じ。このどれかなら `HEAD^` にし、それも無ければ最初の commit にする。
       - 0 の並びは、新しいブランチの push とタグの push で来る。タグの push は、release.yml が ci.yml を呼ぶリリースの道そのもの（Task 2）。履歴に無い基準は、force-push の後に来る。
       - risk.js は基準をそのまま `git diff` に渡し、例外を拾わない（tools/risk.js:224-229）。`node tools/risk.js --base 0000000000000000000000000000000000000000 --head HEAD` は `fatal: bad object` で exit 1 になる（調査者が手元で確認）。
       - 守らないと、タグを打った時に CI が赤になり、リリースが止まる。
    6. **Windows だけ**、`shell: powershell`（pwsh ではない）。
       - `$PSVersionTable.PSEdition` が `Desktop`、`PSVersion.Major` が 5 であることを確かめる。
       - `git ls-files -- '*.ps1'` の全部を、`[System.Management.Automation.Language.Parser]::ParseFile` で解析する。
       - さらに `ParseInput([IO.File]::ReadAllText(p, [Text.Encoding]::GetEncoding(932)))` でも解析する。日本語の PC での読まれ方に合わせるため。
       - 中の文字は ASCII だけにする。
    7. **Windows だけ**: 展開されたバイトが BOM（EF BB BF）と CRLF であること。`git ls-files --eol -- '*.ps1'` が全部 `i/crlf` であること。

### Task 10（R4-1）: tools/ico.js — PNG と ICO を依存なしで扱う

**Files:** 作る `tools/ico.js`、`test/icons.test.js`

**Interfaces**
- `encodePng(width: number, height: number, rgba: Buffer): Buffer`
  - 8bit・色の型 6（RGBA）・各行のフィルタ 0。
  - 圧縮は `zlib.deflateSync`。CRC32 は自前の表で計算する。
- `decodePng(buf: Buffer): { width, height, rgba: Buffer }`
  - 色の型 6・8bit だけを読み、それ以外は投げる。
  - IDAT が複数あれば、つないで `zlib.inflateSync` する。フィルタは 0〜4 を解く。
- `packIco(pngs: Buffer[]): Buffer`
  - 大きさは各 PNG の IHDR から取り、小さい順に並べる。
  - 頭は `00 00 01 00 <個数 2byte>`。
  - 項目は1つ16バイトで、中身は次のとおり。
    - 幅と高さの1バイト（256 のときは 0）
    - 色数 0、予約 0
    - planes 1、bpp 32
    - 大きさ、位置
  - 中身は 6+16n バイト目から隙間なく続ける。
- `parseIco(buf: Buffer): Array<{ width, height, planes, bpp, size, offset, png: Buffer }>`
- コマンド: `node tools/ico.js <out.ico> <in.png>...`

**Steps**
1. 落ちるテストを書く
   ```js

   test('ico.js: PNG を書いて読み戻せる（RGBA 8bit）', () => {

     const png = encodePng(2, 2, rgba);
     assert.deepStrictEqual([...png.subarray(0, 8)], [0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a]);
     const back = decodePng(png);
     assert.deepStrictEqual([back.width, back.height], [2, 2]);
     assert.deepStrictEqual(back.rgba, rgba);

     const ico = packIco([256, 16].map((n) => encodePng(n, n, Buffer.alloc(n * n * 4))));
   ```

## 利用者に確かめること

- **Q1. `.gitattributes` を足してよいか**
  - **足す場合:** `* text=auto eol=lf`、`*.ps1 -text`、`*.bat -text`、画像は binary。
  - **足さない場合:** CI の `core.autocrlf false` だけで、Windows の CI は通る。
  - **判断の材料:** Windows の手元で `npm test` を回すことがあるなら、足すほうがよい。今のままだと、autocrlf=true の clone では 14 件が落ちる（調査者の再現）。
- **Q2. appId の文字列。**
  - 案は `local.natsu.app`（今の `local.listener.app` と同じ形。package.json:27）。
  - 社名と社内アカウント名は repo.test.js:39-40 で使えない。
- **Q3. 起動時に `app.setAppUserModelId('<appId>')` を呼ぶか。**
  - **今の状態:** 呼んでいない（src に0件）。そのため、タスクバーのまとまりと、自動起動の登録の名前（main.js:1919）は、app.name の `natsu` から作られる。一方、ショートカットには appId が付く（NSIS の installer.nsh）。
  - **見出し:** ダイアログは title を渡していない（main.js:841 など）。そのため、見出しが小文字の「natsu」になるかもしれない。
  - **頼みたいこと:** どちらも実機で見て、直すかを決めてほしい。
- **Q4. CHANGELOG の Listener の古い節（v0.8.0〜v0.11.3）をどうするか。**
  - 「Listener（旧名）」の見出しの下に残すか、消すか。
  - どちらでも release.yml の本文の抜き出しは `## natsu-v…` だけを拾う。
- **Q5. 詳細設定の形。**
  - (a) 2枚のエンジンのカードを1枚にまとめてよいか（推奨。状態と起動テストが1つずつになる）。
  - (b) 見出しの文字は「エンジン」でよいか（repo.test.js:601 で固定される）。
  - (c) 「議事録の文字起こし間隔」（segmentSec）も詳細設定へ移すか。
  - (d) カードの起動テストで、要約エンジンも実際に起動して試すか。要約エンジンが未設定のとき、「要確認」とするか（今は任意: app.html:644）。
    - **この計画の既定:** 起動しない（ファイルを見るだけ）。未設定は数えない。
    - 起動すると約 3GB を掴み、記録中は止まらない（main.js:2038-2045, :533、mainlib.js:631）。
    - 実際に起動して試す道は、詳細設定の中の［起動テスト］（`#testSumBtn`）に残す。
  - (e) 新しい IPC `engine:status` を 0a で足してよいか（起動はせず、ファイルを見るだけ）。
  - **答える時期:** (a)(b)(c) は Task 8 の前、(d)(e) は Task 9 の前。既定と違う答えのときの直し方は、Task 8・9 の「始める前に」に書いた。
- **Q6. ロゴの描き方。**
  - **設計書どおり（:157）:** Electron の画面で描く。描くには `npm install` と画面が要る。CI は描けないので、SVG と ICO が食い違っても点の検査でしか気づけない。
  - **代わりの案:** 依存なしの JS の描画器を作る。この SVG が使う命令（絶対座標の M/L/H/V/Q/Z、単色、丸い角と端）だけを描く。CI で SVG と PNG の一致を毎回確かめられる。
  - 代わりの案は調査者が試作し、総当たりの描画と一致した。ただし Chromium の描画とは比べていない。
